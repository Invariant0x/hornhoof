# Map work, returns, and decisions for people

Design for tasks #5 and #6, implementation #13, written under #12. Baseline: `d581edcfe031918e55bc2e91a0b4b4ef6e30f054`. This document proposes changes; it does not claim that the feature or its tests exist. The named implementation modules below are new unless listed in the current-state table.

The map should answer two questions: who is working on an assignment, and which person must decide something. A work edge has one state: blue, yellow for five minutes after a real return, or quiet. Human attention is a separate, persistent signal while decisions remain open. Existing task moves, decision cards, and access checks remain the source of truth. The head confirmed in #12 that ownership changes attention, counts and filtering only: #13 must neither narrow nor expand read, answer, approval or proposal-application rights.

## Work-edge model

Add `apps/server/src/modules/org/map-state.ts` for authoritative work and return projection. Keep message pulses as transient communication effects; they must no longer create, extend, or color persistent work edges. Add shared pure types and the state selector to `packages/protocol/src/map.ts` and export them from its existing entry point. The web consumes that selector through `ui/work-lines.ts`; keep database code on the server.

An edge is identified by its upstream and downstream agent IDs, scoped to the company. Upstream is the orchestrator for a head, and that department's head for a worker. Project a head to its top-level department on the company map. Normalize a product department to its parent; never draw an edge for a missing or removed endpoint. Gate-to-gate traffic can still have one-time pulses; the work color belongs to the head/member relationship, independently of the gate's next recipient.

Persist the work cycle and latest accepted return in a new `map_returns` table in `apps/server/src/db/schema.ts`, including an edge that has started work but has no return yet:

| Field | Meaning |
| --- | --- |
| `company_id`, `upstream_agent_id`, `downstream_agent_id` | Composite primary key; both endpoints must be agents of this company and a valid upstream relationship. |
| `work_epoch` | Nonnegative integer, initially zero; incremented once at each accepted start of qualifying new work on this edge. Never reset on finish, crash, read, reload or server restart. |
| `returned_epoch` | Nullable work epoch stamped on the latest accepted return. A return from an earlier epoch cannot light this edge. |
| `returned_at` | Nullable server timestamp of that committed return; null until a real return exists. |
| `source_key` | Nullable `task:<task-event-id>` or `message:<agent-event-seq>`; repeating a source leaves its original epoch and timestamp unchanged. |
| `source_job_id`, `source_task_id` | Nullable references to the returning turn and assignment; distinguish a job finishing its return from new work. |

Start helper: `recordMapWorkStarted(tx, { companyId, upstreamAgentId, downstreamAgentId, jobId, taskId }): Promise<void>`. After the winning transition actually starts a qualifying assignment, lock its edge row and increment `work_epoch` in the same transaction, before publishing. Hook the accepted start in `conversation/queue.ts` and the alternate start path in `nodes/messages.ts`; include new tasks absorbed by a carrier. A duplicate node acknowledgement, an already-running job, a fetch or a returning job's final output is not a new start. Use the existing guarded job/task transition to ensure one epoch increment per accepted activation; update multiple affected edges in stable order. A delegated worker's start advances both its member edge and the relevant department edge.

Return helper: `recordMapReturn(tx, { companyId, upstreamAgentId, downstreamAgentId, workEpoch, sourceKey, sourceJobId, sourceTaskId, returnedAt }): Promise<void>`. Validate the relationship on the server. Stamp the locked edge's current epoch into the source event's server-owned metadata at first acceptance, then save that exact epoch and timestamp with the return. Replaying the same source must not rebind it to a later epoch; ignore older sources rather than move the clock backwards. A fresh return accepted after a start uses the new epoch even if both timestamps are equal: compare epochs before timestamps. Keep the old return fields when work starts: the epoch mismatch permanently supersedes that return even when `working` becomes false. Persist the source event and return row together, before invalidation. For messages, refactor the durable message insert for that transaction; do not write this fact in the best-effort `handOff` catch block. Source IDs, epochs and times never come from an agent/browser argument.

| Accepted operation | Return recorded |
| --- | --- |
| Executor `submit`, with or without gates | Worker to its head, even when the task's next holder is a reviewer. |
| Executor `blocked`; reviewer `verdict` | Worker to its head. A reviewer's result counts when that reviewer gives its verdict, including when other panel members are still reviewing. |
| Head `report` with either value of `done` | Head to orchestrator, including a block. |
| Head `tell_orchestrator` | Head to orchestrator, at durable acceptance of the message. |
| Worker `message_employee` to its own head | Worker to head, at durable acceptance. Peer messages do not count as returns. |
| Assignment, task comment, request for a person, ordinary job finish, crash, cancellation, status change | No return. A crash or idle state alone cannot turn a line yellow. |

Compute `working` from actual running conversation jobs for assignments, not a recent channel, open task count, any timer run, or `employee.status` alone. An assignment qualifies only while this agent still has an action: executor at stage zero, reviewer still to vote in the current stage/round, or head holding an actionable department task. Exclude blocked tasks, unresolved dependencies, that agent's unanswered request, closed tasks, and completed submissions/verdicts. For the department edge include running delegated work under its actionable department assignments, even while its head sleeps. An unrelated timer/chat job with no assignment must not light it. Switched-off or removed employees contribute no blue edge.

After a return, the returning job often remains `running` while it writes its final answer. Exclude that source job's returned assignment immediately. For an explicit return message without a task, exclude that returning turn from this edge until a new assignment/turn starts. A different, still-actionable assignment may keep an aggregate department edge blue: blue has priority while any relevant work continues. Heads' coalesced tasks need the carrier job relationship from `queue.ts`; do not treat `GONE_ALONG` as finished work or ignore all but `jobs.taskId`. Reuse/extract current stage/panel/dependency checks rather than introducing a second task state machine.

Pure contract: `lineState({ working: boolean, workEpoch: number, returnedEpoch: number | null, returnedAt: number | null }, now: number): 'blue' | 'yellow' | 'quiet'`. Epochs are validated nonnegative integers; times are epoch milliseconds. `RETURN_MS = 300_000` lives with this function in the protocol package.

| Input | State |
| --- | --- |
| `working=true`, any return time | `blue` |
| Not working, `returnedEpoch === workEpoch`, and `0 <= now-returnedAt < RETURN_MS` | `yellow` |
| Epoch mismatch, null return/epoch, expired return, or a future return | `quiet` |

Required sequence on both levels: return in epoch 0 at T -> yellow; actual new work at T+1 minute advances to epoch 1 -> blue; crash or ordinary finish at T+2 without a new return -> quiet, because the saved return still belongs to epoch 0. Only a fresh explicit return stamped in epoch 1 can light yellow again. Persist both epochs so this stays quiet after browser and server restart. This also resolves equal-millisecond start/return ordering without guessing from timestamps.

The snapshot adds `serverNow` (ISO timestamp), `workLines` and each department's `workLines`; existing `live` remains for compatibility with message effects. Each line is `{ upstreamAgentId, downstreamAgentId, working, workEpoch, returnedEpoch, returnedAt }`, with `returnedAt` an ISO timestamp or null. One entry per relationship. Scope new line facts to the viewer's reachable department/product before aggregation; omit inaccessible edges rather than exposing a new return history. No task IDs, job IDs or source keys leave the server in this projection. Line facts are snapshots, not browser event history.

Example fragment of `GET /api/org`: `{ "serverNow": "2026-11-02T12:02:00Z", "workLines": [{ "upstreamAgentId": "<orchestrator-id>", "downstreamAgentId": "<head-id>", "working": false, "workEpoch": 4, "returnedEpoch": 4, "returnedAt": "2026-11-02T12:00:00Z" }] }`. At load it is yellow for another 180 seconds, including after browser reload. If `workEpoch` were 5 with the same old return, it would be quiet. Read these facts in one database snapshot; use one `serverNow` for all its lines, sampled after reading the facts from the same authoritative clock as `returnedAt`.

Publish existing `org` invalidation after a return commits, including a message return without a task move. Task/working invalidations for starts must follow the committed epoch increment and carrier setup; stops never restore an earlier epoch. Use `useOrg`'s fetch sequence protection. The browser estimates server time from the received `serverNow` plus monotonic elapsed time, then schedules the nearest eligible yellow expiry. A repeated fetch must not restart the five minutes. Refetch on reconnect, tab visibility/focus after sleep, and access changes. No new server expiry job or browser storage is needed. A server restart reloads saved epochs and return facts with reconciled job state; it must not infer a return from reconciliation.

Migration: generate a new Drizzle migration, never edit an applied migration. Start `map_returns` empty: existing generic pulses do not prove returns. Historical task events need no speculative backfill. Bounded latest-per-edge rows avoid scanning conversation history on every org read; no extra service, process or node protocol message is needed.

## Decision ownership, visibility, and counts

Add `apps/server/src/modules/tasks/decisions.ts` as the single server projection used by `/api/requests` and `/api/org`. Resolve the owner **at read time**, from current active people and current access. Return `ownerPersonId` in task-request, proposal and computer-access views. There is no persisted owner ID to become stale when access is revoked; `answeredBy` remains the historical actor. Use batch reads and maps, not one access query per decision. Project typed source keys, scope, owner and counts first; only the list route enriches visible rows with explanations, pictures, commit links or the computer's existing view/machine label. Org counts must not build full decision cards.

Owner selection contract: `decisionOwner(decision, taskSpot, activePeopleWithAccess): string`, returning a person ID in the same company:

1. CEO means active `people.isOwner=true`, never any person with `scopeKind=company`. Missing CEO is an explicit server error, not a choice of the first person.
2. Approval of an exact commit, a company-level request, every pending structure/staff proposal, the pending computer-access decision, and a CEO-only topic go to the CEO. Computer access is intrinsically typed as `access`; it has no task and needs no caller-supplied topic.
3. A department task/employee question goes to the sole eligible active non-CEO who can reach its task spot. Every current request has a task: that task's `taskSpot` defines visibility and routing, including an employee question. Do not substitute the asking agent's location or a department mentioned in text. Use the same product/parent semantics as `canReach`; team-only access cannot own a request on a department-wide task it cannot read. If there is no eligible person, use the CEO.
4. With several eligible non-CEO people, use CEO, as the head confirmed in #12 on 2026-11-02. This is a known limitation: shared departmental access concentrates decisions on CEO. Do not use database order or add a new department-owner setting. Invited and disabled people are ineligible.

`question/choice` alone does not encode its subject. Add nullable `requests.decisionTopic`, and optional `topic` to `ask_person`/engine `Ask`. Allowed values: `task`, `employee`, `people`, `access`, `subscriptions`, `machines`, `repositories`, `public_link`, `updates`, `release`. Only the first two permit departmental routing, and only with a department task. Where the server knows the source action's subject, it sets the topic itself: release/commit approval, computer access, people/access, subscriptions, machines, repositories, public link or updates cannot be downgraded by an agent argument. Structure/staff proposals already have typed CEO-only sources. Omitted/legacy unknown topic routes conservatively to CEO; the tool schema tells the agent to specify the subject for new generic questions. Generated task-stuck requests use `task`. Reject unknown topic values and owner-ID overrides; do not infer a privilege-sensitive category from free text or `explained`. Topic classifies a decision; it grants no authority to execute a protected action or create a new administrative approval flow.

Migration adds this column with null for existing rows. Existing approvals still route to CEO; older questions remain answerable without rewriting their text/history. The head confirmed this conservative policy in #12 on 2026-11-02: no legacy-topic data backfill. Known limitation: an old departmental question with unknown subject stays with CEO until answered. Proposals need no schema change: their kind already mandates CEO. Computer access keeps `computer.json` as its sole source; do not copy it to `requests`/`proposals` or add a database migration for it.

**Visibility is independent of ownership.** For a task request, first enforce existing company and `canReach(taskSpot)` visibility. Then apply the optional owner filter. Owning a request never grants access to its task, attachments, employee conversation or terminal. Whole-company viewers can still read all task requests; other viewers read the subset they already reach. Pending proposals retain their existing whole-company visibility, including deputies and `me.via`. The computer-access projection uses its stricter existing `isOwner && !via` guard: deputies, departmental users and the internal orchestrator receive no computer item or contribution to counts, even when selecting the CEO filter. A card's count is the number of its owner's decisions visible to the current viewer, never a hidden company-wide total exposed through `/api/org`. For another person's unseen total use null. Whole-company viewers see task/proposal totals; only the real CEO's total includes computer access. Each departmental owner sees their own full count. Existing task detail/history and attachment routes keep their checks.

**Mutation authorization stays unchanged in #13.** POST `/api/requests/:id` retains `reachable`/`canReach` and `requireCompanyScope` for approvals. Any person who can currently answer a visible question/choice/stuck request can still answer it even when `ownerPersonId` names someone else. Whole-company deputies retain approvals and existing build/staff proposal application. Keep `answerDirectly` unchanged for conversation and terminal paths through `modules/tasks/wake.ts`; the orchestrator's `answer_request`, `me.via` behavior, existing `CEO_ONLY` tool set and `answersCeo` checks also remain unchanged. Do not add owner checks, new errors, internal job headers or new `answersCeo` gates. Preserve current task-then-request lock order and `409 request_closed`. Compute `canAnswer` from these existing permissions only, never from ownership. The narrower policy proposed during design is separate CEO work below, not #13 scope.

Computer access never enters that generic answer flow. Reuse `/api/computer/open`, `/api/computer/decline` and `/api/computer/close`, preserving their existing strict real-CEO guard and `403 not_owner`, plus `409 updater_missing` on open when unavailable. A chat/terminal answer, `answer_request`, generic request POST or `me.via` cannot resolve it. Preserve `ComputerCard`'s existing actions and the CEO-origin wake after opening. A failed open leaves the pending decision counted until its source actually clears it.

## Paths, attention, and motion

For each work relationship draw a single persistent SVG path using the canonical geometry: `deptLayout(...).path` for orchestrator/head, the complete head/member route from `stepPaths` for the department view. Extend the geometry helper with `workLine(memberId): Point[] | null` if necessary; the line must end at both cards, even where existing gate paths only cover a segment. Blue/yellow are classes on this one path. Use `fill:none`, a solid stroke, `stroke-dasharray:none`, no dash animation, `vector-effect:non-scaling-stroke`, and the existing cyan/amber tokens. A yellow full-length stroke is independent of any traveling dot, gradient, zoom, or browser timing. Prevent old persistent `live` overlays from covering these relationships. Remove state-change-generated yellow shots that would imply a return without a server return fact.

People with one department currently have no chip in the company map's top row. For rendering, build a stable, deduplicated `mapPeople(org)` from `org.people` and `departments[].people`; use it consistently in layout, bounds, hit targets and `pulsePath`. Keep server placement and department membership intact. This makes every person's card reachable from the hub without changing access. Department copies of the card use the same count and navigation handler, never add to totals again.

When `pendingDecisions>0`, draw a dedicated path from the visible hub boundary to that person's chip, ordered hub-to-person, with a solid amber base and the existing repeating `Pulse` in the forward direction (`bounce=false`). Keep it separate from work edges and transient messages. Two owners have independent paths/counts, even along a shared bus. The person's frame and hub breathe gently using a new attention class; text and count stay opaque. Hub attention is true when any **visible** person's count is positive. Answering the last visible decision removes that person's badge, attention and signal immediately after the refreshed snapshot.

Use real buttons for people, visible focus rings, translated accessible labels including the count, pointer cursor, and the existing pan/drag suppression. Zero/null count has no badge or signal; the card can still open the filtered empty/visible list. Hub click keeps the existing orchestrator handler. Listed users retain the existing noninteractive hub: a decision does not give access to the orchestrator's company-wide conversation. With `prefers-reduced-motion`, keep calm solid amber frames/paths, remove CSS breathing and SVG `animateMotion`, and react if the preference changes while the screen is open.

## Risks and calls made by this design

- **Access is the main risk.** Filter before ownership/counts, preserve writes at every entry point, and never let human attention open a previously forbidden orchestrator window. Ownership is routing, not a permission grant or revocation. The head confirmed the unchanged authorization boundary in #12 after Developer's review; the authorization regression matrix is a gate requirement. General People/Machines/etc. administration routes remain out of scope.
- **Explicit facts versus channel reuse.** A saved work epoch plus a return's epoch/timestamp and current-work projection cost one small table and start/return hooks. Timestamp-only returns were rejected: old yellow would reappear after new work crashes or finishes silently. Reusing pulses also cannot distinguish submit-to-reviewer from return-to-head, durable restart, or arbitrary traffic. Historical backfill from generic pulses was rejected because it would invent returns.
- **Read-time versus stored owner.** Read-time resolution keeps revocation/disable correct and avoids backfill of stale owner IDs. It costs batched projection on reads. Storing an owner would need reassignment transactions across every access and task-scope change. Only the topic is saved; mutation authorization continues its current checks.
- **Confirmed routing limitations.** The head chose CEO fallback for zero/several active non-CEO candidates, rather than a new explicit department-owner setting. The head also chose CEO for unknown/legacy topics rather than guessing `task` and possibly reassigning a sensitive question. Shared access and older unclassified questions can therefore increase the CEO's queue. Both decisions are recorded in #12's log.
- **Separate sources are real decisions.** Counting only `requests` misses proposals and `ComputerAccess.view().asked`. Project all three typed sources without manufacturing task IDs or duplicate rows. Multiple pending staff cards can coexist; computer access is a persisted singleton with stricter read/write rights. The latest conversation event cannot substitute for either source, and a broad generic answer flow cannot substitute for ComputerCard's guarded endpoints.
- **Work correlation is the first implementation spike.** Pin submit's still-running tail, delegated work and `GONE_ALONG` in server tests before UI work. If current job/task association cannot prove an active assignment, keep that edge quiet and bring the concrete gap to the head rather than treat every busy employee as blue.
- **Clock and fetch races.** Server event time plus `serverNow` avoids the browser starting five minutes at reload. Use monotonic elapsed time and visibility/reconnect refetch; no optimistic event may manufacture a return. Counts across two HTTP calls converge, while each response is internally consistent.
- **No product code in #12.** This note's verification is source-path and requirement review. The feature, runtime tests and browser acceptance remain #13's work; no dependencies or services are needed to review the document.
