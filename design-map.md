# Map work, returns, and decisions for people

Design for tasks #5 and #6, implementation #13, written under #12. Baseline: `d581edcfe031918e55bc2e91a0b4b4ef6e30f054`. This document proposes changes; it does not claim that the feature or its tests exist. The named implementation modules below are new unless listed in the current-state table.

The map should answer two questions: who is working on an assignment, and which person must decide something. A work edge has one state: blue, yellow for five minutes after a real return, or quiet. Human attention is a separate, persistent signal while decisions remain open. Existing task moves, decision cards, and access checks remain the source of truth.

## Work-edge model

Add `apps/server/src/modules/org/map-state.ts` for authoritative work and return projection. Keep message pulses as transient communication effects; they must no longer create, extend, or color persistent work edges. Add shared pure types and the state selector to `packages/protocol/src/map.ts` and export them from its existing entry point. The web consumes that selector through `ui/work-lines.ts`; keep database code on the server.

An edge is identified by its upstream and downstream agent IDs, scoped to the company. Upstream is the orchestrator for a head, and that department's head for a worker. Project a head to its top-level department on the company map. Normalize a product department to its parent; never draw an edge for a missing or removed endpoint. Gate-to-gate traffic can still have one-time pulses; the work color belongs to the head/member relationship, independently of the gate's next recipient.

Persist the latest accepted return in a new `map_returns` table in `apps/server/src/db/schema.ts`:

| Field | Meaning |
| --- | --- |
| `company_id`, `upstream_agent_id`, `downstream_agent_id` | Composite primary key; both endpoints must be agents of this company and a valid upstream relationship. |
| `returned_at` | Server timestamp of the committed source event. |
| `source_key` | `task:<task-event-id>` or `message:<agent-event-seq>`; repeating this source leaves the timestamp unchanged. |
| `source_job_id`, `source_task_id` | Nullable references to the returning turn and assignment; distinguish a job finishing its return from new work. |

New helper contract: `recordMapReturn(tx, { companyId, upstreamAgentId, downstreamAgentId, sourceKey, sourceJobId, sourceTaskId, returnedAt }): Promise<void>`. Validate the relationship on the server. Upsert only a newer accepted event; a late older source cannot move the clock backwards. Persist with the source operation, before publishing invalidation. For messages, refactor the existing durable message insert so its source event and the return record commit together; do not write this fact in the best-effort `handOff` catch block. Source IDs and times come from the server, never from an agent/browser argument.

| Accepted operation | Return recorded |
| --- | --- |
| Executor `submit`, with or without gates | Worker to its head, even when the task's next holder is a reviewer. |
| Executor `blocked`; reviewer `verdict` | Worker to its head. A reviewer's result counts when that reviewer gives its verdict, including when other panel members are still reviewing. |
| Head `report` with either value of `done` | Head to orchestrator, including a block. |
| Head `tell_orchestrator` | Head to orchestrator, at durable acceptance of the message. |
| Worker `message_employee` to its own head | Worker to head, at durable acceptance. Peer messages do not count as returns. |
| Assignment, task comment, request for a person, ordinary job finish, crash, cancellation, status change | No return. A crash or idle state alone cannot turn a line yellow. |

Compute `working` from actual running conversation jobs for assignments, not a recent channel, open task count, any timer run, or `employee.status` alone. An assignment qualifies only while this agent still has an action: executor at stage zero, reviewer still to vote in the current stage/round, or head holding an actionable department task. Exclude blocked tasks, unresolved dependencies, that agent's unanswered request, closed tasks, and completed submissions/verdicts. For the department edge include running delegated work under its actionable department assignments, even while its head sleeps. An unrelated timer/chat job with no assignment must not light it. Switched-off or removed employees contribute no blue edge.

After a return, the returning job often remains `running` while it writes its final answer. Exclude that source job's returned assignment immediately. For an explicit return message without a task, exclude that returning turn from this edge until a new assignment/turn starts. A different, still-actionable assignment may keep an aggregate department edge blue: blue has priority while any relevant work continues. Heads' coalesced tasks need the carrier job relationship from `queue.ts`; do not treat `GONE_ALONG` as finished work or ignore all but `jobs.taskId`. Reuse/extract current stage/panel/dependency checks rather than introducing a second task state machine.

Pure contract: `lineState({ working: boolean, returnedAt: number | null }, now: number): 'blue' | 'yellow' | 'quiet'`, all times epoch milliseconds. `RETURN_MS = 300_000` lives with this function in the protocol package.

| Input | State |
| --- | --- |
| `working=true`, any return time | `blue` |
| Not working, `0 <= now-returnedAt < RETURN_MS` | `yellow` |
| Null return, expired return, or a future return | `quiet` |

The snapshot adds `serverNow` (ISO timestamp), `workLines` and each department's `workLines`; existing `live` remains for compatibility with message effects. Each line is `{ upstreamAgentId, downstreamAgentId, working, returnedAt }`, with `returnedAt` an ISO timestamp or null. One entry per relationship. No task IDs, job IDs or source keys leave the server in this projection. Request arrays and line facts are snapshots, not browser event history.

Example fragment of `GET /api/org`: `{ "serverNow": "2026-11-02T12:02:00Z", "workLines": [{ "upstreamAgentId": "<orchestrator-id>", "downstreamAgentId": "<head-id>", "working": false, "returnedAt": "2026-11-02T12:00:00Z" }] }`. At load it is yellow for another 180 seconds, including after browser reload. Read these facts in one database snapshot; use one sampled `serverNow` for all its lines.

Publish existing `org` invalidation after a return commits, including a message return without a task move. Existing task/working invalidations cover starts and stops; ensure the final invalidation follows carrier setup too. Use `useOrg`'s fetch sequence protection. The browser estimates server time from the received `serverNow` plus monotonic elapsed time, then schedules the nearest yellow expiry. A repeated fetch must not restart the five minutes. Refetch on reconnect, tab visibility/focus after sleep, and access changes. No new server expiry job or browser storage is needed. A server restart reloads saved return facts and reconciled job state.

Migration: generate a new Drizzle migration, never edit an applied migration. Start `map_returns` empty: existing generic pulses do not prove returns. Historical task events need no speculative backfill. Bounded latest-per-edge rows avoid scanning conversation history on every org read; no extra service, process or node protocol message is needed.

## Decision ownership, visibility, and counts

Add `apps/server/src/modules/tasks/decisions.ts` as the single server projection used by `/api/requests` and `/api/org`. Resolve the owner **at read and answer time**, from current active people and current access. Return `ownerPersonId` in both task-request and proposal views. There is no persisted owner ID to become stale when access is revoked; `answeredBy` remains the historical actor. Use batch reads and maps, not one access query per decision.

Owner selection contract: `decisionOwner(decision, taskSpot, activePeopleWithAccess): string`, returning a person ID in the same company:

1. CEO means active `people.isOwner=true`, never any person with `scopeKind=company`. Missing CEO is an explicit server error, not a choice of the first person.
2. Approval of an exact commit, a company-level request, every pending structure/staff proposal, and a CEO-only topic go to the CEO.
3. A department task/employee question goes to the sole eligible active non-CEO who can reach its task spot. Every current request has a task: that task's `taskSpot` defines visibility and routing, including an employee question. Do not substitute the asking agent's location or a department mentioned in text. Use the same product/parent semantics as `canReach`; team-only access cannot own a request on a department-wide task it cannot read. If there is no eligible person, use the CEO.
4. Several eligible people is an unresolved policy question below; do not silently use database order. Invited and disabled people are ineligible.

`question/choice` alone does not encode its subject. Add nullable `requests.decisionTopic`, and optional `topic` to `ask_person`/engine `Ask`. Allowed values: `task`, `employee`, `people`, `access`, `subscriptions`, `machines`, `repositories`, `public_link`, `updates`, `release`. Only the first two permit departmental routing. The server forces CEO for approvals/company tasks/proposals regardless of the supplied topic. Omitted/legacy unknown topic routes conservatively to CEO; the tool schema tells the agent to specify the subject for new questions. Generated task-stuck requests use `task`. Reject unknown topic values and owner-ID overrides; do not infer a privilege-sensitive category from free text or `explained`. Topic classifies a decision; it grants no authority to execute a protected action.

Migration adds this column with null for existing rows. Existing approvals still route to CEO; older questions remain answerable without rewriting their text/history. The choice of routing legacy unclassified department questions is called out below. Proposals need no schema change: their kind already mandates CEO.

**Visibility is independent of ownership.** For a task request, first enforce existing company and `canReach(taskSpot)` visibility. Then apply the owner filter. Owning a request never grants access to its task, attachments, employee conversation or terminal. CEO can read all; other viewers can only read the subset they already reach. A card's count is the number of its owner's decisions visible to the current viewer, never a company-wide total exposed through `/api/org`. For an inaccessible person's decisions omit the count (`null`), rather than inventing zero. CEO sees full counts; each departmental owner sees their own full count. Existing task detail/history and attachment routes must keep their checks; ownership fields added there obey the same policy.

Mutation checks must share the same resolver in POST `/api/requests/:id`, `answerDirectly` (conversation plus terminal through `modules/tasks/wake.ts`), and orchestrator `answer_request` through the existing internal route. A human answers their own departmental requests; CEO may answer visible departmental requests as an override. CEO-only requests and proposal application require CEO; whole-company deputies are not CEOs. The orchestrator may act for CEO only from a running CEO-origin job (`jobs.answersCeo=true`) for these CEO-only decisions. A request-explanation/task/timer turn must not approve or apply one autonomously. Extend the server-only internal context in `auth/internal.ts`/`auth/session.ts` with the source job ID from `modules/tools/control.ts`; verify its company, agent, running status and `answersCeo` in the decision/proposal mutation guard. An arbitrary external header or `me.via` alone is insufficient. Keep `explain_request` available to explanation turns. Scope ownership and permission checks to the transaction's current access/request state, preserve the existing task-then-request lock order, and retain `409 request_closed` for racing answers. Return stable `403 decision_not_yours`/`ceo_only` for visible forbidden actions and `404 request_unknown` for invisible or foreign decisions. Do not broaden unrelated administrative endpoints as part of this task.

## API and existing screen

Extend `GET /api/requests` additively:

- Optional strict query `person=<uuid>` filters by `ownerPersonId` **after** visibility. Unknown/inaccessible/foreign person gets the same empty visible result; invalid UUID/unknown query field is `400 validation`. Omitted person returns all visible decisions, preserving the existing default. This filter is not an authorization token.
- Keep `requests` with every existing field, including plain-language `explained`, adding `ownerPersonId` and viewer-specific `canAnswer`.
- Add `proposals`: pending structure/staff proposals visible only to CEO and the existing internal orchestrator view. Each has `id`, `kind`, `agent`, `department`, `brief`, validated `items`, `at`, `ownerPersonId`, `canAnswer`. Use `proposals.status`, not the latest conversation event, as the pending source.
- Add `counts: { byPerson: Record<string, number>, byAgent: Record<string, number>, total: number }`, computed from the full **authorized, unfiltered** snapshot. Counts stay stable when a person filter changes. A decision's key is `(request|proposal, id)`; each counts once, even if shown in two places. Order each collection by `(createdAt, id)`; retain the existing complete-open-list behavior rather than truncating counts to a page. Pagination is outside this change.

Example request: `GET /api/requests?person=<ceo-uuid>`. Example shape: `{ "requests": [{ "id": "<request-id>", "ownerPersonId": "<ceo-uuid>", "canAnswer": true, "...": "existing fields" }], "proposals": [], "counts": { "byPerson": { "<ceo-uuid>": 1 }, "byAgent": { "<asking-agent-id>": 1 }, "total": 1 } }`. Angle-bracket IDs are placeholders, not valid sample UUIDs.

In `/api/org`, attach `pendingDecisions: number | null` to both top-level and departmental person views, calculated by this same projection: the visible `byPerson[id]` value when present, otherwise zero for self/CEO viewers and null for another person's unseen total. Null conveys no company-wide zero. Do not add it to unrelated `/api/people` output. `byAgent` is the asking employee's count; existing request lists and waiting states continue to derive from the same open rows. The navigation total includes pending proposals now. At one authorized snapshot: `sum(byPerson) = sum(byAgent) = total = requests.length + proposals.length` before an owner filter. Do not count waiting employees, closed tasks, answered/withdrawn requests, superseded/applied proposals or a human reply as additional decisions.

`Shell.tsx` owns `decisionPersonId: string | null` and the handler `onOpenDecisions(personId)`. Pass it to both map and department cards. It selects the existing Tasks tab, closes the department overlay, and shows the existing requests section with a visible person chip and a clear-filter button. `tasks.ts` retains one full authorized decision snapshot; local filtering uses the server's owner field. The query filter is available for independent callers, but navigating this UI must not replace the full snapshot used by navigation and task panels. Ordinary Tasks navigation clears the filter. CEO clears it to see all decisions they may read.

Reuse `Requests`, `StructureCard` and `StaffCard` in that section. Proposal actions keep the existing build/staff endpoints and `proposalId` conflict checks; a callback reloads both decisions and org. Opening a person card does not create a task or decision. A read-only visible request uses `canAnswer=false`; keep its explanation readable without showing reply controls. New labels and errors go into both `apps/web/src/i18n/en.ts` and `ru.ts`.

Publish `requests` invalidation after ask/answer/withdraw/cancel and proposal create/replace/apply/dismiss, including dismissal during department removal. For proposal-only changes use the company-level spot, so only whole-company viewers receive them. After people/access changes, including acceptance, disable and reinvite, publish `org` and make the decision hook refresh too; ownership is a read projection. Use minimal invalidations, never broadcast a hidden request body, owner ID or count. On access changes refresh/clear stale decision and org state before displaying a new snapshot; server authorization still governs every read and write. Reconnect refetches both snapshots; separate requests may briefly reflect different commits but must converge on the next invalidation.

The person's frame and hub breathe gently using a new attention class; text and count stay opaque. Hub attention is true when any **visible** person's count is positive. ## Risks and calls made by this design

- **Access is the main risk.** Filter before ownership/counts, enforce writes at every entry point, and never let human attention open a previously forbidden orchestrator window. The CEO-only application checks deliberately tighten the current whole-company check for proposals/approvals. General People/Machines/etc. administration routes remain out of scope.
- **Explicit facts versus channel reuse.** A saved return row and a current-work projection cost one small table and hooks; reusing pulses is smaller but cannot distinguish submit-to-reviewer from return-to-head, durable restart, or arbitrary traffic. Historical backfill from generic pulses was rejected because it would invent returns.
- **Read-time versus stored owner.** Read-time resolution keeps revocation/disable correct and avoids backfill of stale owner IDs. It costs batched projection on reads and reauthorization at writes. Storing an owner would need reassignment transactions across every access and task-scope change. Only the topic is saved.
- **Proposals are real decisions.** Counting only `requests` would miss the acceptance example. Add them to the existing response/section as a separate typed collection; do not manufacture task IDs or duplicate requests for them. Multiple pending staff cards can coexist, so taking just the newest conversation event is insufficient.
- **Work correlation is the first implementation spike.** Pin submit's still-running tail, delegated work and `GONE_ALONG` in server tests before UI work. If current job/task association cannot prove an active assignment, keep that edge quiet and bring the concrete gap to the head rather than treat every busy employee as blue.
- **Clock and fetch races.** Server event time plus `serverNow` avoids the browser starting five minutes at reload. Use monotonic elapsed time and visibility/reconnect refetch; no optimistic event may manufacture a return. Counts across two HTTP calls converge, while each response is internally consistent.
- **No product code in #12.** This note's verification is source-path and requirement review. The feature, runtime tests and browser acceptance remain #13's work; no dependencies or services are needed to review the document.
