You can prepare and publish an authorized software version with evidence and a tested way back.

Read the task, project release procedure and actual required gates. Follow the project's approved version scheme; for a pre-1.0 product use 0.x.y. Where a turn-number scheme is approved, a turn N ships as X.N.0 and a release between turns increments the patch once. Only the authorized human decides a major-version increase; explain incompatible changes and rollback limits before approval.

1. Confirm that the exact candidate contains only intended changes and that its required checks really passed. Never skip, mute or retry a failed check merely to get green. Read all part logs and commit IDs; a green author test does not prove another stage. External Review and Security engineers work only in echelon tasks. In an echelon task, any change affecting access, root, permissions or secrets must pass an independent Security engineer before it reaches any shared branch, including the turn's branch, for urgent and small work and review fixes too; self-review does not replace this gate. A member of a turnkey team does and releases its task end to end alone, with its own review and security check, and calls no external checker.
2. Set the version consistently in the project's manifests and lockfile. Prepare release notes once, from the tasks the release brings, with the date as one short list in the repository's language, with no translations: one-line entries under Fixed, Added and Changed, in that order, with no summary; a step people must take before updating is the first entry under Changed, starting with "Before you update:". Attach the review materials people need.
3. Merge the ready work into the turn's branch (or a release branch): the run of every test happens there once, through run_tests; a failed release is mended, and its next run runs only what failed or changed; then main moves. The turn branch never stops for a release: others keep taking finished work into it while the run and the approval take their time, and the release takes the commit its whole run checked. Run types, quality checks and artifact builds in your own workspace under the project's release authorization. Pin dependencies, protect CI secrets and verify artifact revision/digest. Never publish an unapproved task branch.
4. Prove rollback first: prior version/artifact, exact command, compatible data/schema and owner of each machine. The checks of step 3 on the exact candidate are the release's proof; another commit does not prove it.
5. On a department's turn, record its release with release_turn before main moves: the commit of the turn branch its whole run checked, which the branch may have gone past (what came after it goes into the next release), a passed whole run of it, and the person's approval of that commit, or none under the department's autonomous release when every commit of it was checked; the version tag on main then closes the turn by itself. On another release task leading to main, ask with commit before pushing (ask_person or request_approval channel commit) and push only after the answer says no card is needed, or after the person's yes. With the department's autonomous release on, an exact 40-character current candidate from main (review.baseCommit on main) with a completed green whole run, an independent non-author PASS verdict on that SHA (plus Security PASS when required) and a complete fast-forward comparison from main gets recorded auto-approval without sending a human card; otherwise (off, missing check, non-main branch or diff over limit) present the exact 40-character commit, version, notes, required verdicts, test evidence and rollback record to the person who approves the department's releases: its owner, or the CEO when it has none. Obtain their explicit yes for that exact candidate; a skill, employee or earlier approval cannot substitute for it.
6. Merge only the approved commit into main by the project's approved method, then publish its version/artifacts. Build its images or artifacts only from that approved commit, by the project's release route, and preserve the final publication gate. Do not infer a production update permission from artifact preparation.
7. Verify the published/deployed revision and health, record the result and preserve the rollback path. Apply employee cards or restart live programs only when separately authorized, while idle, preserving model/provider and active work.

When a check or access condition is unavailable, report that exact blocker rather than weakening it or asking a person to run private technical commands. This ability works for any appropriately authorized employee; role identity does not choose a release owner or grant publication access.
