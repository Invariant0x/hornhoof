You can prepare and publish an authorized software version with evidence and a tested way back.

Read the project's release procedure, actual gates and version scheme. Derive the next version from its published versions and compatibility promises. Explain any breaking change and the limits of rollback to the people responsible for the release.

1. Confirm that the exact candidate contains the intended changes and that its assigned checks passed. Read all part outputs and commit identifiers. Never skip, mute or retry a failed check merely to get green. Preserve the evidence and scope of each check. External Review and Security engineers work only in echelon tasks. In an echelon task, any change affecting access, root, permissions or secrets must pass an independent Security engineer before it reaches any shared branch, including the turn's branch, for urgent and small work and review fixes too; self-review does not replace this gate. A member of a turnkey team does and releases its task end to end alone, with its own review and security check, and calls no external checker.
2. Set the version consistently in the project's manifests and lockfile. Keep the changelog in the repository's required language. Write user-facing release information and required update steps in the languages in which the release is presented.
3. Freeze the checked release candidate on an eligible release or configured integration branch. The release relies on the repository's own CI for that exact commit: read its checks, the commit each one names and its conclusion on the repository's host, and never replace them with a run of your own machines. Keep progressing later work while CI checks the frozen candidate. Pin dependencies, protect secrets and verify the revision of the build artifacts.
4. Prove rollback first: prior version/artifact, exact command, compatible data/schema and owner of each machine. The repository's CI on the exact candidate is the release's proof; another commit does not prove it.
5. Record the checked release revision with release_turn where the project uses turns, before moving the integration branch. Hornhoof reads the repository's CI for that exact commit itself, from the GitHub Actions runs of it: green CI records the release with no run, red or unfinished CI refuses and names the failing check and its link, and a repository with no CI records with no run. Green means every job of every run finished with success; commit statuses and the checks of other apps prove nothing and are never read. Only the full runs of the repository's release workflow count, the workflow a person named in the repository settings (never one Hornhoof picks; with none named release_turn refuses and says to name it), a run started by hand with its input full, which runs every test and ends its run title with (full run); a skipped test job makes the run red. Where no such run is on the commit yet, release_turn starts that workflow with full set on the turn branch itself, once for each commit, answers that CI started, and the minute round records the release when CI is green and tells you; a token that cannot start workflows or a workflow that takes no input full refuses and says why. A repository on another host than github.com refuses as unreadable, never as having no CI. When there is no approval rule, integrate on the required evidence. If the department set a commit rule, apply it to the exact checked candidate through the authorized decision or autonomous proof path. When the applicable autonomous route accepts turnkey evidence, use its holder's own review, security check and tests. Check every eligibility requirement of that path against the current run, candidate and integration target. Where recorded automatic approval requires independent proof, verify the repository's green CI on the exact commit (or none where the repository has no CI), an independent non-author PASS on the same commit, Security PASS when required, and a fast-forward from the integration target.
6. Move main to the exact checked commit by the project's authorized method, using approval of that commit where required. Build and publish artifacts from that commit by the project's release route. On a turn the version tag on main closes the turn. Follow any separate policy for a production update.
7. Verify the published/deployed revision and health, record the result and preserve the rollback path. Apply employee cards or restart live programs only when separately authorized, while idle, preserving model/provider and active work.

When a check or access condition is unavailable, report that exact blocker rather than weakening it or asking a person to run private technical commands. This ability works for any appropriately authorized employee; role identity does not choose a release owner or grant publication access.
