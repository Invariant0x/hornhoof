Review work marked `small: true` in the shared turn review, using its affected-test result and the turn's quality results. Do not require separate task reports, matrices, complexity metrics or duplicate checks; the numbers and evidence requirements below apply to the shared scope for this work.

You review work you did not write. Read the brief and the review scope in `task` first:

- **First look**: runs at your role's or card's base level. When a change exceeds roughly 800 lines, `task.reviewPlan` (`threshold: 800`) splits it across two reviewers on providers that did not author that slice (`authorVendor`), by vertical task slices and not by folders. Read your assigned slice (`baseCommit..commit` and `paths`) together with `commonContracts` (protocol definitions, database schemas and route schemas, such as `packages/protocol`, `schema.ts` and route schemas); when you are `integrationReviewerId`, also check cross-slice connections and boundaries. If no independent non-author provider is available, `task.reviewPlan` marks the review `degraded` or blocked under policy; an author's provider never self-passes as an independent check. Below the threshold, read what the branch changed and the code around it.
- **Second look (`task.fixReview`)**: opens only where the rules give one, at a single-task gate return or a conditional follow-up on a blocking `security`, `data` or `spec` finding, and only for the same reviewer who raised it, at medium. Read strictly the immutable commit range `reviewed_commit..fix_commit` (`task.fixReview` `reviewedCommit..fixCommit`) and check only the fixes for your own prior blocking `findingIds`. Unchanged code brings no new findings or `issues`. The general review of a turn stays one round: ordinary fixes after it start with a failing test that then passes, and are covered by the author's verification, the turn's final check and QA acceptance, with no second general turn review.

**Your program's own review on a first look only**, from inside the clone on the branch or slice you review (the turn's branch in the review of a turn): in Claude Code its code-review skill, in Codex `codex review --base <main line>`, in Antigravity its review-agent subagent. Kimi Code has none. Keep the turn's assigned effort without raising it. Its findings are leads: check each against the code, then go through the list below, which it does not replace. On a second look, skip your program's own review and never reread the whole patch, whole branch or full diff.

1. **Does it do what the brief asked?** Every requirement met, nothing extra added. Missing work is a finding.
2. **Correctness.** Walk the real inputs through the code: empty, very large, wrong type, duplicate, concurrent, the error path. Name the input and the wrong result for each problem.
3. **Silent failures.** Errors caught and dropped, fallbacks that hide a broken state, defaults that turn a failure into a wrong answer, promises nobody awaits.
4. **Data.** Migrations safe for existing rows, transactions where two writes must agree, nothing trusted from outside without a check at the boundary.
5. **Obvious security problems.** An entry point that does not check who asks, input that reaches a query, command or path unchecked, a secret in code, logs or errors. Deeper checks of access, sign-in, secrets and permissions are the security gate's.
6. **Tests (T1, T6).** Do they fail without the change, and does every bug or review fix start with a failing test? Do they test behaviour, not mocks? Ask for an additional test only when you name the concrete harm to a person that happens without it (T6); low coverage alone is not a finding (T1).
7. **The engineering rules and the rules of each language** (dev-language-rules). Duplication, a decision in two places, a function doing three things, a silenced check, dead code.
8. **The numbers.** Read the test engineer or QA's `crapper` and `dryer` results from the shared final check, verifying their commit and scope against the turn's change (`git diff --name-only --diff-filter=d <main line>...HEAD`). Missing or unverified results remain unproved; send the gap to the head for the assigned tester, rather than running tools or requiring metrics from the author. A duplicate scoring 0.8 or more is blocking, like a failing test, unless the brief says why it stays; so is a function at CRAP 10 or more that is new or whose cyclomatic complexity the change raised against the main line. A function at CRAP 10 or more whose complexity did not grow is old complexity: a note with its numbers on the main line and now, and a separate refactoring task to propose. It does not stop the review, and nobody asks the head for an exception. Authors submit affected tests and SHA; these shared checks run once per turn on the final candidate through `run_tests` (`hh-run-checks`).
9. **Simplicity.** Code that could be half as long and still clear.

Verify what the executor proved on the reviewed commit instead of rerunning the author's test runs (T10): check `task.review` (`commit`, `runs` run ID and number, `verified`, and `gateCounts`), `testEvidence` (`run`, 40-character `commitSha` and `proves: true`), `requirement -> test` links and screenshots. Do not rerun the author's test runs; a run on another commit proves nothing about what you review. Missing browser evidence goes to the test engineer or QA's final check. Mutation testing follows T4 and belongs to the assigned tester once per turn on the final candidate, from the repository root against selected pure logic and its fast tests. The selection and its reason must be visible in the result. As a reviewer you do not run mutator.

Every finding has a place (file and line), category (`security`, `data`, `spec`, `other` or `mechanical`), what goes wrong, and the harm to a person. Assign `mechanical` only when a fix provably cannot change behaviour: formatting or lint fixes, a safe local rename, or adding a missing translation key inside that strict boundary, whereas renaming a public API or altering semantics is never automatically `mechanical`. When in doubt, pick the regular category so follow-up work runs at the full base level; never classify `security` or `data` or `spec` or behavioural issues as `mechanical` to run at `medium`. Only when every structured issue across the failing verdicts is `mechanical` (with at least one `blocking` issue and no `unresolvedFindingIds`) does the server set `Wake.mechanical`, keeping mixed or legacy or repeat verdicts unmarked; this review procedure never sets effort, never changes effort inside a running turn, and never opens a second review. Your findings go only in your verdict: write to nobody while you review, as each message opens a turn for its reader. Only what blocks sends the work back (dev-review-verdict); the rest are notes under a pass. On a second round, check only the fixes for your own blocking `findingIds` in `reviewed_commit..fix_commit`. Check each finding against the code before you report it; a wrong finding costs the author an hour. Then give your verdict with dev-review-verdict.
