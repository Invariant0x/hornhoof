You can enforce the department's batch route and its applicable checks.

Read the current assignment, task acceptance, declared risk and actual gates (the route in task.echelons) before acting. A coding task's own route is Development only: a developer writes code and tests, checks only what the change touches and hands the branch on, then takes the next task. Review, Security and Tests run once each on the whole turn branch, after every slot has landed. Each stage fixes what it finds on that branch and reruns its own check; nothing returns to the developer who wrote the code. Architecture is on request, as a fork from Development ahead of the work, not a stage of every task; Performance runs alongside and serves every pipeline of the department. One current owner writes a branch at a time. Roles supply independent abilities; a role name or numeric gate never determines the current stage.

Review checks correctness, simplicity and basic security of the whole batch, records confirmed findings and repairs them on the turn branch within the assigned paths. A result pursuing the wrong goal goes to the head. The checker is another employee with a model not weaker than the producer; prefer another provider when one is available. The same provider, subscription or tariff is allowed without waiting for a second provider.

A batch stage may hold several members, and the head picks one of two modes for it. "Pieces": the head splits the batch into parts, and each member checks and fixes only their part. "Whole batch each": every member takes the whole turn branch independently. In both modes each member works on their own branch cut from the turn branch and fixes what they find there, with no returns. When all of them are done, the head merges their branches into one and hands it to the next stage; after Tests, the head merges the turn, deletes the spent branches and releases. Members on the same subscription use "pieces", for speed; "whole batch each" is only for members on different subscriptions or models. Keep one member of a stage for each distinct subscription the department has.

Cleanup is absent by default. Only the head enables this optional stage for a turn. Then it follows Review and uses the existing cleanup ability, offered to developers and reviewers but switched off by default. It removes unnecessary work on the turn branch.

Security reads the whole turn branch once, after Review and before Tests, and fixes what it finds there; nothing goes to main without that pass; the hotfix lane's fix gets its own Security read before its patch release. Security is also required for personal data and outside-input boundaries. The head can set the required check at assignment; Review can add it with a concrete reason. Keep a required check open if no eligible checker is available, and tell the head what must be resolved. Do not expand access to find a checker.

When broader validation is assigned, one owner freezes the exact candidate. Tests verifies the exact final candidate including Review, optional Cleanup and Security repairs. Select only applicable checks for the changed code. A new or changed test always runs. Mutate only changed pure functions with direct fast tests; database, process and network code does not enter that mutation scope. Read full finished logs. Missing, refused or unsupported checks are NOT_RUN, never PASS. Change checks run in the checker's own workspace. Do not duplicate unchanged passed checks. Tests fixes what it finds, in source or in tests, on the turn branch. For integration drift only, when the candidate's own change passed and it only needs the main line or the open turn branch of its own department taken in, the owner of the stage merges the current head of that line into its branch and checks again.

A coordination group without its own executable output closes with a checked report once every child is done or cancelled, whichever way each closed. The report references accepted current child candidates and evidence, and records a child with no accepted current result as closed without one, never as accepted. Only open child work blocks closure. A parent with its own executable output follows the same batch stages; its title grants no exemption.

After Tests, integrate only by the task's authorized route. Follow the department's commit rule for main and release, and its publication rule for publication. If main needs approval, ask for the exact commit before pushing. Use the responsible person's answer, the answer of the orchestrator acting for the owner, or recorded pre-push auto-approval under autonomous release. Follow the separate authorization for live updates. Ability selection grants no permission to release or change another person's machine.
