You can enforce the required development route and its applicable checks.

Read the current assignment, task acceptance, declared risk and actual gates (the required route in task.echelons) before acting. Every executable work result of an echelon task passes Review. A small task skips Architecture; other work starts with a concrete plan. Development produces code and tests. One current owner writes the task branch at a time. Roles supply independent abilities; a role name or numeric gate never determines the current stage.

Review checks correctness, simplicity and basic security, records confirmed findings and repairs them in the same branch within the assigned paths. Ordinary findings never return to the original author. A result pursuing the wrong goal goes to the head. The checker is another employee with a model not weaker than the producer; prefer another provider when one is available. The same provider, subscription or tariff is allowed without waiting for a second provider.

Cleanup is absent by default. Only the head enables this optional stage for a task or turn. Then it follows Review and uses the existing cleanup ability, offered to developers and reviewers but switched off by default. It removes unnecessary work in the same branch without returning it to the author.

External Review and Security engineers work only in echelon tasks. In an echelon task, any change affecting access, root, permissions or secrets must pass an independent Security engineer before it reaches any shared branch, including the turn's branch, for urgent and small work and review fixes too; self-review does not replace this gate. A member of a turnkey team does and releases its task end to end alone, with its own review and security check, and calls no external checker. In an echelon task Security is also required for personal data and external-input risks. The head enables it at assignment; Review can add it with a concrete reason. The Security engineer checks and repairs the sensitive result before authorized integration. If an eligible reviewer is unavailable, keep the candidate waiting and tell the head. Do not skip a required stage or expand access to find a checker.

When broader validation is assigned, one owner freezes the exact candidate. Tests verifies the exact final candidate including Review, optional Cleanup and Security repairs. Select only applicable checks for the changed code. A new or changed test always runs. Mutate only changed pure functions with direct fast tests; database, process and network code does not enter that mutation scope. Read full finished logs. Missing, refused or unsupported checks are NOT_RUN, never PASS. Change checks run in the checker's own workspace. Do not duplicate unchanged passed checks. Nothing goes back to an earlier stage: when the candidate's own change passed and it only needs the main line or the open turn branch of its own department taken in, it stays at Tests, whose owner merges the current head of that line into its branch, uses "submit" with review.baseCommit naming the commit taken in and checks again.

A coordination group without its own executable output closes with a checked report once every child is done or cancelled, whichever way each closed. The report references accepted current child candidates and evidence, and records a child with no accepted current result as closed without one, never as accepted. Only open child work blocks closure. A parent with its own executable output follows the same required Review route; its title grants no exemption.

After Tests, integrate only by the task's authorized route. Follow the department's commit rule for main and release, and its publication rule for publication. If main needs approval, ask for the exact commit before pushing. Use the responsible person's answer, the answer of the orchestrator acting for the owner, or recorded pre-push auto-approval under autonomous release. Follow the separate authorization for live updates. Ability selection grants no permission to release or change another person's machine.
