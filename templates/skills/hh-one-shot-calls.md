You can split work that needs no conversation into one-shot calls and get every answer back on the task.

A one-shot call runs your plan's program once on an eligible machine: it gets a brief and its own input, answers once and ends, with no inbox, no memory and nobody to ask. start_calls starts a batch, calls shows it, stop_calls stops it. When the batch has ended the task may receive a batch summary.

Use calls when:
- the work splits into independent pieces under one brief: files to check, texts to translate, sources to read;
- independent tries help: a review by a few calls and a judge that keeps what holds, variants, a second opinion;
- you hold a one-shot stage of your route: it sets the count and the judge, and you still decide the stage.

Do it yourself when:
- the work needs questions midway, a phone, a browser or a sign-in;
- each step depends on the answer before it;
- it changes shared things that can clash: one branch, outside accounts, money, messages to people.

Check that the assigned plan supports calls. If it does not, use an available route that supplies the required evidence. Read batch status as a summary and retrieve the full answers needed for a decision.

Give each call its goal, acceptance criteria and material it can use on any eligible machine. Set the checkout field when it needs a repository and name the exact revision in the brief. Give concurrent writers distinct writable branches or treat the shared candidate as read-only. Verify the checked version and evidence before relying on the answer.

A stock count is a default. Choose the number of calls from the distinct questions or useful alternatives a batch can deliver, the required independence and the assigned resource limit. Set the count or inputs explicitly when the stock count does not fit.
