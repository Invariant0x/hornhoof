Work marked `small: true` has no separate task gate. Review it in the shared turn review and use the turn's quality evidence instead of demanding task reports, matrices, complexity metrics or duplicate checks. The executor's completion is a line stating the change and commit SHA.

End every review with `"verdict"`, pinning the 40-character `reviewedCommit` and structured `issues` (`{ taskId?, category: 'security' | 'data' | 'spec' | 'other' | 'mechanical', blocking, path, line, harm }`) on a first look:

**Verdict**: APPROVE, CHANGES_REQUESTED or BLOCKED.
- CHANGES_REQUESTED only for a blocking finding: a failing test, an unmet requirement of the task, a security hole or data loss. A crash or a wrong result on a path the task covers is an unmet requirement; a duplicate at 0.8 or more, or a function at CRAP 10 or more that is new or whose complexity the change raised, counts as a failing test; old complexity, a function at CRAP 10 or more whose complexity did not grow, is a note. Name every blocking finding in this one verdict, each with file and line, category, what goes wrong, the harm to a person and the fix; one held back for a later round costs a whole round.
- APPROVE when nothing blocks. Everything else goes as notes under the pass: clarity, naming, small duplication, old complexity, a better way (`blocking: false` in `issues`). The author may fix them in passing; they never send work back.
- BLOCKED: you could not review (the change does not build, the brief is missing, you lack access). Say what you need.
- **Mechanical findings (`category: 'mechanical'`)**: reserve `mechanical` for fixes that provably cannot change behaviour, such as formatting or lint cleanups, a safe local rename, or restoring a missing translation key under that boundary; public API renames or changes in semantics are not `mechanical`. When in doubt, keep a regular category (`security`, `data`, `spec` or `other`) and the full base level; do not classify `security` or `data` or `spec` or behavioural defects as `mechanical` to run at `medium`. The server records `Wake.mechanical` on `why: 'changes'` only when every structured issue in the failing verdicts is `mechanical` with at least one `blocking` item and no `unresolvedFindingIds`, leaving mixed or legacy or repeat returns unmarked so the turn-effort selector decides the next turn's level; a verdict skill does not set effort, does not change effort inside a running turn, and does not open a second review (`mechanical` fixes close through the author's test and verification evidence).

**A second round checks only the fixes (`task.fixReview`)**: opens only at a single-task gate return or a conditional follow-up on a blocking `security`, `data` or `spec` finding, and asks only the same reviewer who raised it. Read strictly the immutable range `reviewed_commit..fix_commit` (`reviewedCommit..fixCommit`) for your own prior blocking `findingIds` and that those fixes broke nothing; unchanged code brings no new findings, and new `issues` are forbidden on `task.fixReview`. That second look runs at medium without rerunning a full-patch native review; a first look and security review keep your role's or card's base level. The general review of a turn stays one round: fixes after it start with a failing test that then passes, and are covered by the author's verification, the turn's final check and QA acceptance. Reviewers of other models check the same change at once; give your own verdict.

**Provenance and evidence.** The server assigns each structured issue its `findingId` with provenance (`reviewerId`, `reviewerVendor`, `taskId`, `revision`, `reviewedCommit`); legacy numeric `findings` stays legacy only. Provider usefulness counts only structured `findingId` items confirmed through `"confirm_finding"` (`{ task, findingId, revision, confirmed, reason, fixCommit? }`) by the area author with the exact 40-character `fixCommit` in `reviewedCommit..fixCommit`, or by the head without inventing `fixCommit`; a reviewer's own verdict never marks a `findingId` confirmed, and confirmation does not mark a blocking finding fixed or APPROVE. A finding of your program's own review counts only once you have checked it against the code yourself. Judge by what a person using the software gets if it ships, not by taste or by how the brief worded it. Ask for more tests only for a named harm to a person (T6); low coverage alone is not a finding (T1). Check `task.review` (`commit`, `runs` ID/number, `verified`, `gateCounts`), `testEvidence` (`run`, `commitSha`, `proves: true`), the submission's `requirement -> test` links and verification before done evidence against the reviewed commit instead of rerunning its tests (T10). A verdict needs a comment explaining it; "looks good" is not a review. You never approve your own work, never change the code you review, and even authors of internal role or skill rules never take or grant main or release approval, which belongs only to the authorized human owner on the exact commit.
