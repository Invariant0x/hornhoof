The check itself is a skill of its own, the review of a change or the security review. This skill is what a gate adds to it, and it applies only when you judge someone else's change: you never approve your own work and never change the code you review.

Work marked `small: true` has no separate task gate. Review it in the shared turn review and use the turn's quality evidence instead of demanding task reports, matrices, complexity metrics or duplicate checks. The executor's completion is a line stating the change and commit SHA.

Do not demand final metrics from each author: they come from the testing gate (dev-testing-policy). Your findings go only in your verdict: write to nobody while you review, as each message opens a turn for its reader.

**The scope of a look.** Read the brief and the review scope in `task` first.

- **First look**: runs at your role's or card's base level. When a change exceeds roughly 800 lines, `task.reviewPlan` (`threshold: 800`) splits it across two reviewers on providers that did not author that slice (`authorVendor`), by vertical task slices and not by folders. Read your assigned slice (`baseCommit..commit` and `paths`) together with `commonContracts` (protocol definitions, database schemas and route schemas, such as `packages/protocol`, `schema.ts` and route schemas); when you are `integrationReviewerId`, also check cross-slice connections and boundaries. If no independent non-author provider is available, `task.reviewPlan` marks the review `degraded` or blocked under policy; an author's provider never self-passes as an independent check.
- **Second look (`task.fixReview`), a second round that checks only the fixes**: opens only at a single-task gate return or a conditional follow-up on a blocking `security`, `data` or `spec` finding, and asks only the same reviewer who raised it, at medium. Read strictly the immutable range `reviewed_commit..fix_commit` (`reviewedCommit..fixCommit`) for your own prior blocking `findingIds` and that those fixes broke nothing; unchanged code brings no new findings, and new `issues` are forbidden on `task.fixReview`. On a second look, skip your program's own review and never reread the whole patch, whole branch or full diff.
- **The review of a turn** stays one round: fixes after it start with a failing test that then passes, and are covered by the author's verification, the turn's final check and QA acceptance. Reviewers of other models check the same change at once; give your own verdict.

**The verdict.** End every review with `"verdict"`, pinning the 40-character `reviewedCommit` and structured `issues` (`{ taskId?, category: 'security' | 'data' | 'spec' | 'other' | 'mechanical', blocking, path, line, harm }`) on a first look:

- CHANGES_REQUESTED only for a blocking finding: a failing test, an unmet requirement of the task, a security hole or data loss. A crash or a wrong result on a path the task covers is an unmet requirement; what T11 says blocks counts as a failing test. Name every blocking finding in this one verdict, each with file and line, category, what goes wrong, the harm to a person and the fix; one held back for a later round costs a whole round.
- APPROVE when nothing blocks. Everything else goes as notes under the pass: clarity, naming, small duplication, old complexity, a better way (`blocking: false` in `issues`). The author may fix them in passing; they never send work back.
- BLOCKED: you could not review (the change does not build, the brief is missing, you lack access). Say what you need.
- **Mechanical findings (`category: 'mechanical'`)**: reserve `mechanical` for fixes that provably cannot change behaviour, such as formatting or lint cleanups, a safe local rename, or restoring a missing translation key under that boundary; public API renames or changes in semantics are not `mechanical`. When in doubt, keep a regular category (`security`, `data`, `spec` or `other`) and the full base level; do not classify `security` or `data` or `spec` or behavioural defects as `mechanical` to run at `medium`. The server records `Wake.mechanical` on `why: 'changes'` only when every structured issue in the failing verdicts is `mechanical` with at least one `blocking` item and no `unresolvedFindingIds`, leaving mixed or legacy or repeat returns unmarked so the turn-effort selector decides the next turn's level; a verdict skill does not set effort, does not change effort inside a running turn, and does not open a second review (`mechanical` fixes close through the author's test and verification evidence).

**Provenance and evidence.** The server assigns each structured issue its `findingId` with provenance (`reviewerId`, `reviewerVendor`, `taskId`, `revision`, `reviewedCommit`); legacy numeric `findings` stays legacy only. Provider usefulness counts only structured `findingId` items confirmed through `"confirm_finding"` (`{ task, findingId, revision, confirmed, reason, fixCommit? }`) by the area author with the exact 40-character `fixCommit` in `reviewedCommit..fixCommit`, or by the head without inventing `fixCommit`; a reviewer's own verdict never marks a `findingId` confirmed, and confirmation does not mark a blocking finding fixed or APPROVE. A finding of your program's own review counts only once you have checked it against the code yourself. Judge by what a person using the software gets if it ships, not by taste or by how the brief worded it. Ask for more tests only for a named harm to a person (T6); low coverage alone is not a finding (T1). Check `task.review` (`commit`, `runs` run ID and number, `verified`, `gateCounts`), `testEvidence` (`run`, `commitSha`, `proves: true`), the submission's `requirement -> test` links, screenshots and verification before done evidence against the reviewed commit instead of rerunning its tests (T10); missing browser evidence goes to the testing gate. A verdict needs a comment explaining it; "looks good" is not a review. Even authors of internal role or skill rules never take or grant main or release approval, which belongs only to the authorized human owner on the exact commit.
