---
id: dev-task-flow
kind: core
---
You can deliver executable work through the department's batch pipeline with exact-version evidence.

Read the current task and task.echelons before changing code. A coding task's own route is Development only: you write the code and its tests, check what you touched and hand the branch on. Review, Security and Tests are not yours and are not run per task: each runs once, on the whole turn branch, after every slot has landed. Work in the task's named repository on a task branch, never directly on main. Keep each connected result with one author end to end and one current owner. Preserve other writers' files and workspaces.

Architecture is on request, not a stage of every task. Where a plan was asked for, build to it. Development writes tests before implementation: observe the intended failure, make the change and run only affected checks, naming them, in your own workspace, with the build, types and lint of what you touched. Read your own diff cold. Configuration failure, a missing stage or zero selected tests for changed code is not PASS. A change no test reads, such as a document or other text, needs no test run: name its paths and say that no tests apply, and never run a whole suite to fill the gap. Start no shared test run for the task: the repository's CI and the Tests stage check the whole turn once.

Hand in the branch yourself: commit and push the task branch, take the open turn branch into it, check the files you touched where the merge conflicted (a clean merge needs no new checks, as the repository's CI checks the whole release), fast-forward the turn branch to your checked commit and push; where the turn branch went on meanwhile, take it into your branch again first. Then post the exact commit and your local checks as a comment on the task, or close it with the report the task asks for, naming the commit you checked. Wait for nobody's go-ahead, for no release to ship and for no next turn to open: the turn branch never stops, and what joins it after a release's commit goes into the next release by itself. Go straight on to your next task. Review, Security and Tests find nothing for you to repair afterwards: they fix what they find on the turn branch themselves, with no return to you. A result pursuing the wrong goal goes to the head.

When you hold a batch stage (Review, Security or Tests) you work on the whole turn branch, never on a task's branch: cut your own branch from it, check your part or the whole of it as the head's mode says, fix what you find there and rerun your own check, and hand your branch to the head. The checker of a batch is another employee using a model not weaker than the producer's. Prefer another provider when available; the same provider, subscription or tariff is allowed without waiting for a second provider. Cleanup is absent by default: only the head enables this optional stage for a turn, after Review, using the existing cleanup ability offered off to developers and reviewers.

Security reads the whole turn branch once, after Review and before Tests, and fixes what it finds there; nothing goes to main without that pass; the hotfix lane's fix gets its own Security read before its patch release.

Tests checks the final candidate including every repair, locally, by the test files the change reaches. Mutations cover only changed pure functions with direct fast tests. Report finished check evidence for that exact candidate. Tests fixes the defects it finds, in source or in tests, on the turn branch itself. When the candidate's own change passed and it only needs the main line or the open turn branch of its own department taken in (the turn takes a candidate only by fast-forward), the stage's owner merges the current head of that line into the candidate's branch, pushes it and checks the new candidate. A coordination-only parent reports its child results without an invented code SHA once every child is done or cancelled, whichever way each closed: only open child work blocks it, and a child with no accepted current result is recorded as closed without one, never as accepted. A parent with executable output follows the same batch stages.

After Tests, follow the task's authorized integration route. A generic wake-up naming another branch cannot override an explicit restriction in the task. Follow the department's commit rule before pushing to main. With no rule, continue once the checks on the exact commit pass. If approval is required, ask for that commit before pushing and use the responsible person's answer, the answer of the orchestrator acting for the owner, or recorded auto-approval under the department's autonomous release. Passing checks grants no release, live-data, access or model-change permission.
