You can obtain a check result on the right machine without duplicating another owner's work.

- First: we test our program, not the operating system and not other programs. A test never checks or waits for another program's work; our side of it (starting it, its input, parsing its output) is tested on a recorded sample of that output. A test gives the same result on any machine: nothing in it depends on machine speed, the clock, a random port or unsorted order.
- Second: time in a test is virtual only. No test waits for or measures real time: no deadline, wait or pause on the real clock; it uses a controlled clock, a direct call of the step, or a wait for an event or state with no deadline. These two rules rank above superpowers. Where its test-driven-development skill (SKILL.md and writing-good-tests.md) says to exercise the real thing and use real code, and where its systematic-debugging/condition-based-waiting.md says to wait on the real clock with a timeout (waitFor with timeoutMs), our rule applies here: other programs and the system appear in a test only as recorded samples or fakes, time is only virtual, and nothing waits on the real clock.
- When authoring or reviewing a change, run its checks right away in your own workspace on your own machine. Name one or more regular test files in the command. Include new tests and callers; read the complete result. The assignment identifies the check scope and any broader check owner; do not start a duplicate full run merely because this ability is present.
- A whole suite is a test runner given no test file, or a selection it cannot name file by file: a directory, glob, loop or variable. Only a whole suite or declared profile uses "run_tests", split into groups over free compatible machines on the pinned commit. Never use watch modes or task runners that run everything in your terminal.
- Install dependencies from the lockfile in your workspace once, and again when the lockfile changes. When the repository's test environment manifest names its dependencies, they are already in place when you start, so install only when they are missing or after the lockfile changes. Run locally: builds, types, lint/format, coverage, crapper, dryer and mutation of changed code. Named browser test files run in the workspace when the browser is there; browser installation is allowed. The whole browser suite across engines uses "run_tests". A lightweight single-page screenshot capture is not a browser suite.
- Existing "run_work" may prepare dependencies for non-check work under its ordinary rights; it is not test evidence, and any check in a work run still uses "run_tests". Keep your own change checks in your own workspace; do not carry them to another machine.
- Read a valid passed receipt for the same candidate or fingerprint instead of running it again. A stale result, a collection-only selector result or a command refusal is not PASS.
- If the whole-suite route or a compatible environment is unavailable, report "blocked" with what is missing. Never fall back to a local whole suite or manufacture success. The task can assign you a broader final check; owning this ability alone does not.
