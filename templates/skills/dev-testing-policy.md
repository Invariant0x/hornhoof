This is the one place that says who runs which check and when. Other skills point here. It fits any company, project and language.

### How the engineering rules apply here

The engineering rules (ub-mode) are kept word for word, so the company's own ways are written here, and here wins where they differ:

- **Commit and Push.** The main line of a task is the branch the task names, usually the turn's branch. Push your branch, not the main line: the project's main line takes a commit only after the gates and the CEO's approval.
- **Keep a Log.** What you report on completion is your submission: the tests written, the green affected-test result and commit SHA.
- **Crapper, Dryer and Mutator.** They run as T11 and T4 say, never as a check of one task or fix round.

### Policy

- T1. Put logic in pure functions with direct fast tests: milliseconds, no database, network or processes. At each seam, such as a route or an outside-world boundary, use only the integration tests that cover its contract and named failures, usually one or two, and few end-to-end tests. Write no tests just for coverage. Split a function with CRAP above 10 first. Test races, locks, role permissions and migrations of existing data on the product's real database, where it has one, in the final run.
- T2. Developers run only affected tests through run_tests, using the project's selector, such as vitest related, jest --findRelatedTests, pytest --testmon, go test of affected packages or cargo test -p, or the selector commands the repository documents; never assume `run_tests` selects by itself. A new test file always runs, even when no graph edge reaches it. Keep an explicit project list of paths outside import graphs: migrations, schema, configuration, environment, routes, fixtures, string tables, scripts, installation, updates, shared packages, API contracts and templates. A change to such a path, an unsupported language, an unavailable selector or any doubt selects the complete affected package, never an empty selection. Database migrations run both up and down; when either direction is unsupported, report it explicitly. A selection step that could not run stays `NOT_RUN`. Selection and execution are distinct evidence: a collected graph proves which units were selected, only completed test receipts on that exact commit prove execution, and missing full-suite comparator evidence is `unavailable`, not zero misses. The run record keeps selector input, selected inventory, fallback reasons, run, part and commit outcomes. Submit the tests written, the green result and commit SHA. When the final run finds what selection missed, record a selection miss and return it to the author as a test task.
- T3. Use this same check table everywhere:

| Stage | Checks |
|---|---|
| Small task (`small: true`) | Failing test, change and only affected tests; extra checks at the shared turn review. |
| In work (ordinary tasks) | Failing test, change and only affected tests through run_tests (T2). |
| After a batch merges | The batch's affected tests on one pinned commit. |
| Final turn candidate | Test engineer or QA: the whole suite, typecheck of tests and applications, build, language checks, browser engines where the product has a web interface, mutation, coverage and CRAP, dryer, and the real database and live program checks where the product has them. |

  The whole suite runs only for the final turn candidate, never on a task, a fix round or a batch. Every check names its commit; its evidence counts while that is the commit being reviewed. A large run may be split across machines only when the split pays for itself and its parts take roughly equal time. A flaw in logic goes back to its author as a task, small fixes by the fast path; the test engineer or QA fixes a flaky or outdated test or an obvious trifle itself, in a separate commit. After fixes run only what failed and the tests around it.
- T4. The test engineer or QA runs mutator, Stryker, PIT, Infection or mull once per turn on the final candidate, only on the riskiest pure logic the turn changed and only against its fast tests; never on a task, a fix round or against tests using a database, processes or network. The assigned tester selects changed pure functions without database, network or process imports by CRAP and change size, plus everything on money, access and security paths, within the release check's time budget; the selection and its reason must be visible in the result. Skip dry code such as logs, string tables and configuration literals, with at most one mutant per line. Use covering tests and past results where the tool supports perTest and incremental runs. In monorepos run mutator from the repository root (`--root .`), selecting package tests through the workspace. Report killed, survived, uncovered, compile_error and timeout separately; compile errors and timeouts are not kills. A configuration error or zero tests fails the run. Survivors go to the line's author as direct fast tests; record why an equivalent mutant is equivalent. Only money, access and security logic blocks the release; other survivors become tasks for the next turn. Where the manifest makes mutation a suite of the final profile, `run_tests` does the running: a file that did not change keeps its last result, shown again with the run's result, and a changed file reruns only survivors and rewritten functions; the tester reads the survivors there and applies this rule, as a survivor alone does not fail the run.
- T5. Do not mass-rewrite old slow tests. New code follows T1; rewrite a slow test only when its code is already changing.
- T6. Review asks for more tests only for a named harm to a person; low coverage alone is not a finding. Every bug fix still starts with a failing test that reproduces it.
- T7. Measure suite speed every turn. The performance line records time by package and part and tests slower than the median of its package by a chosen factor. Limits are relative, never fixed minutes.
- T8. Test checks in other departments the same way. Code checks, such as an email gate, a response gate or financial recomputation in SQL or a script, have fast unit tests, including cases they must reject. Model checks, such as ticket classification, brand and promise review or design criticism, use a versioned set of examples with known answers, labelled by someone other than its author and with a part hidden from the author. Run that set when the check, its prompt or the provider model changes, not on every item, and count false accepts and false rejects separately. The department owner sets the acceptance threshold. Every error found in life becomes an example.
- T9. Keep tests deterministic (F.I.R.S.T.): date, timezone, test order, randomness and ids do not change the result. Shared test helpers set clocks, timezone and seed. Fix a flaky test by its cause, without retries or quarantine. Once per turn, run the final suite in shuffled order.
- T10. Evidence is a run, not a paraphrase. A submission attaches the actual result and names the same commit that is reviewed; the reviewer checks that evidence instead of rerunning the tests. A result parser that counts any result a success is broken evidence.
- T11. The test engineer or QA runs crapper and dryer once per turn on the final candidate, through `run_tests`, from the repository root on what the turn changed, `git diff --name-only --diff-filter=d <main line>...HEAD`: `--changed` sees only uncommitted files. A language they do not support stays `NOT_RUN`, never a pass. They take coverage from an already completed run and never start a second coverage run. A duplicate scoring 0.8 or more is blocking, like a failing test, unless the brief says why it stays; dryer compares changed code with existing code too. So is a function at CRAP 10 or more that is new or whose cyclomatic complexity the change raised against the main line. A function at CRAP 10 or more whose complexity did not grow is old complexity: a note with its numbers on the main line and now, and a separate refactoring task to propose. It stops nothing, and nobody asks the head for an exception.
