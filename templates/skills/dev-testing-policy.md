You can plan and read proportionate verification for an assigned software candidate.

**The first rule: we test our program, not the operating system and not other programs.** **The second rule: time in a test is virtual only.** No test waits for or measures real time: not one deadline, wait or pause on the real clock, and no check of elapsed time. A test drives time with a controlled clock (fake timers or the code's injected clock), calls the step directly, or waits for an event or a state with no deadline; the runner's limit on a whole test is the only limit. A test gives the same verdict on any machine at any load. Every rule below follows these two.

- **Our side only.** For another program (an agent program such as Claude Code, Codex, Kimi Code or Antigravity, tmux, a package manager, a test runner, a linter, a browser driver) or the operating system, test only our side: we started it correctly, passed it the input and parsed its output correctly, that output coming from a recorded sample. Delete a test that checks or waits for another program's work or output; we do not test or guarantee that another program works.
- **Virtual time only.** A deadline of our code that a test needs to run out runs out on the controlled clock; one that must not run out never runs on the real clock in the test. A pause in a test is replaced by waiting for the state, an event or a direct call of the step.
- **Same result on any machine.** Keep out of tests what does not depend on our code: machine speed, the real clock, random ports and unsorted data order. Take ports only from the project's narrow test port range. A release test gives the same result on any machine.
- **Unstable tests.** Establish whether instability exposes an intermittent product defect or a faulty check. Preserve proof of harmful behavior and rejection cases. Replace faulty checks with reliable evidence; record any remaining gap.
- **Delete, never skip.** A deleted test is never replaced by a skip. Delete it with the code only it needs, and keep our code it checked covered by an our-side test on a recorded sample where one can be written.
- **Our screens stay.** Browser tests of our own web screens in three engines stay: that is our program. A task's check, local or a run of the shared runner, runs its browser test files in Chromium only; Firefox and WebKit run in the repository's CI for the exact commit of a release, which checks that a screen looks the same in all three engines.
- **Protected checks.** Never weaken a check of our own code's access rights, identity or secret redaction.

Read the task's acceptance, gates and employee assignment first. They identify the actual checker and scope; this ability does not assign a downstream tester, a shared turn review or a fixed role chain. Use the check assigned by the owner for small work. Use a visual or shared check alone only when the project permits it and it proves the change. A full validation is a distinct assigned scope, not a consequence of selecting this ability.

- **T1: Test behavior.** Put logic in pure functions with direct fast tests. At boundaries use narrow integration checks for the named contract and failure; keep only a few end-to-end flows. Test races, locks, permissions and data migrations on the real database when that risk is part of the check. Do not write tests merely for coverage or that duplicate a constant's spelling.
- **T2: Select impact explicitly.** A task's check runs only that task's files and the tests selected for them: no whole suite and no extra parts, and not on the shared runner: it runs in your own workspace. During code authoring or review run affected tests in your own workspace right away, naming each test file. Use the project's selector to collect that inventory. The author's check runs, with coverage, the tests that import a changed file directly, are named after a changed source, or changed in the commit. The rest of the tests the import graph reaches are listed by file in its record as left to the repository's CI, which checks the release. Use the shared runner (`run_tests`) for a task's checks that need more machines, on the configured integration branch or an eligible release candidate branch; the release inventory itself runs in the repository's CI for the exact commit a release records. A new test file always runs. For migrations, schema, configuration, environment, routes, fixtures, string tables, scripts, installation, updates, shared packages, API contracts and templates, use the project's declared out-of-graph policy; an unavailable adapter or an unbounded impact takes the complete affected package rather than an empty selection. Migrations need fresh and upgraded data and both up/down when supported; report unsupported down explicitly. Collection is not execution: keep NOT_RUN for an unavailable selector, completed exact-version receipts for executed tests, and unavailable rather than zero for an absent full-suite comparator. Record input paths, selected inventory, fallback reason, command and commit.
- **T3: Match the assigned scope.** A small change uses its chosen check and a short report. An ordinary implementation uses its affected tests locally on its task branch. Neither runs the whole suite, which the repository's CI runs for the release. A batch verifies the affected merged candidate. If assigned full candidate validation, one owner coordinates it: the repository's CI for the exact candidate, plus application/test types, build/language checks, the three browser engines where relevant, quality measurements and actual database checks; no test in that stage checks or waits for another live program's work. Run that full stage once for its candidate; after a fix rerun failed and affected checks unless evidence of wider impact justifies more. Do not repeat a full stage on every author or merely because a role name suggests it.
- **T4: Sample semantic mutation.** When mutation is assigned, select changed risky pure functions without database/network/process imports, prioritizing money, access and security. Use covering tests and incremental results where the tool supports them. Keep dry strings/configuration out; at most one mutant per line. Report killed, survived, uncovered, compile_error and timeout separately; errors/timeouts are not kills, and configuration failure or zero tests is not a pass. The project/task's risk policy determines what blocks; money/access/security survivors require explicit resolution. Do not invent a clean metric from unavailable tooling.
- **T5: Compare performance under comparable conditions.** Judge a regression against a documented workload, a comparable baseline and the project's stated performance or cost requirement. Correctness does not depend on host speed.
- **T6: Name the harm.** Request extra tests for a concrete possible wrong result, not low coverage alone. A bug fix starts with a failing regression. For a permitted visual-only check, name exactly what visual behavior is proved.
- **T7: Measure useful timing.** Record the scope and conditions of file, package or run timings. Compare with the relevant baseline and investigate excess work with a measurable impact.
- **T8: Prove automated checks.** Test arithmetic and code checks with executable rejection cases. For model judgments record their acceptance evidence and fallback owner with the result.
- **T9: Keep checks deterministic.** Control clocks, timezone, ordering, random seeds, IDs and ports. Diagnose unexpected results and preserve checks of access, identity and secret redaction. Do not retry or quarantine a failing check to get a green result. Use shuffled-order verification when the assignment calls for it.
- **T10: Read receipts.** Evidence is the actual run and its complete log for the reviewed commit. A change check an author or reviewer ran in their own workspace, recorded with its command, output and commit, is such a run. A parser treating every outcome as success is broken. Reuse a passed result only when its exact candidate/fingerprint and scope apply; do not rerun a proved check for appearances. Missing, refused, stale or collection-only evidence is never PASS.
- **T11: Read quality measures honestly.** Use measures validated for the project and applicable coverage from a completed run. Investigate a threshold crossing where it exposes a concrete defect or maintenance cost. Record the finding or reason to accept it and keep unsupported or unavailable measures marked NOT_RUN.
- **T12: Let a running run finish.** Never stop a running check run to start a new one for a small fix: wait for its result and fix from it, so the next run proves the fix together with whatever else that result showed. Stop a run only when it is broken, such as one with a wrong command or on the wrong commit.
- **T13: One run at a time.** The Tests stage holds at most one run of the shared runner, queued or running, for the turn branch: start the next only once the last has ended, so the shared check machines stay free for others' runs. A developer starts none for a task.

Install dependencies from the lockfile in your workspace once, and again when it changes. After you check out another commit or make a worktree, prepare its dependencies and the builds of the repository's own packages again, as the repository says, before a check: a "cannot find" of the repository's own package is a stale preparation, not a failed check. Run builds, types, lint/format, coverage, quality and changed-code mutation locally. Named browser test files also run there when the browser is present; installing it is allowed into a folder of your workspace named by `PLAYWRIGHT_BROWSERS_PATH`. A node's shared browser folder already holds the browsers of the repository's Playwright version and may be read-only: never install into it, and where a repository's own script installs browsers before its tests, run its test runner directly. Stop only processes you started, by their process id. Never stop them by name or pattern, as `pkill` or `killall` do: on a shared machine that ends other employees' checks. Report a blocked route with its exact missing condition. Check results do not grant access, authorize publication or replace independent Security before a sensitive shared-branch integration.
