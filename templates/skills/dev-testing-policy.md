You can plan and read proportionate verification for an assigned software candidate.

**The first rule: we test our program, not the operating system and not other programs.** **The second rule: time in a test is virtual only.** No test waits for or measures real time: not one deadline, wait or pause on the real clock, and no check of elapsed time. A test drives time with a controlled clock (fake timers or the code's injected clock), calls the step directly, or waits for an event or a state with no deadline; the runner's limit on a whole test is the only limit. A test gives the same verdict on any machine at any load. Every rule below follows these two.

- **Our side only.** For another program (an agent program such as Claude Code, Codex, Kimi Code or Antigravity, tmux, a package manager, a test runner, a linter, a browser driver) or the operating system, test only our side: we started it correctly, passed it the input and parsed its output correctly, that output coming from a recorded sample. Delete a test that checks or waits for another program's work or output; we do not test or guarantee that another program works.
- **Virtual time only.** A deadline of our code that a test needs to run out runs out on the controlled clock; one that must not run out never runs on the real clock in the test. A pause in a test is replaced by waiting for the state, an event or a direct call of the step.
- **Same result on any machine.** Keep out of tests what does not depend on our code: machine speed, the real clock, random ports and unsorted data order. Take ports only from the project's narrow test port range. A release test gives the same result on any machine.
- **Unstable tests.** Weaken or delete an unstable test quickly; do not spend long diagnosing it.
- **Delete, never skip.** A deleted test is never replaced by a skip. Delete it with the code only it needs, and keep our code it checked covered by an our-side test on a recorded sample where one can be written.
- **Our screens stay.** Browser tests of our own web screens in three engines stay: that is our program.
- **Protected checks.** Never weaken a check of our own code's access rights, identity or secret redaction.

Read the task's acceptance, gates and employee assignment first. They identify the actual checker and scope; this ability does not assign a downstream tester, a shared turn review or a fixed role chain. Use the check assigned by the owner for small work. Where a simple visual change may use a visual/shared check without a separate test, honor that choice without waiving protected approvals. A full validation is a distinct assigned scope, not a consequence of selecting this ability.

- **T1: Test behavior.** Put logic in pure functions with direct fast tests. At boundaries use narrow integration checks for the named contract and failure; keep only a few end-to-end flows. Test races, locks, permissions and data migrations on the real database when that risk is part of the check. Do not write tests merely for coverage or that duplicate a constant's spelling.
- **T2: Select impact explicitly.** During code authoring or review run affected tests in your own workspace right away, naming each test file. Use the project's selector to collect that inventory. The author's check runs, with coverage, the tests that import a changed file directly, are named after a changed source, or changed in the commit. The rest of the tests the import graph reaches are listed by file in its record as left to the full run of the release. Check what you touched with local tests of the files it reaches; every test runs together once per release, on the turn's branch or a release branch before main, or on main. A new test file always runs. For migrations, schema, configuration, environment, routes, fixtures, string tables, scripts, installation, updates, shared packages, API contracts and templates, use the project's declared out-of-graph policy; an unavailable adapter or an unbounded impact takes the complete affected package rather than an empty selection. Migrations need fresh and upgraded data and both up/down when supported; report unsupported down explicitly. Collection is not execution: keep NOT_RUN for an unavailable selector, completed exact-version receipts for executed tests, and unavailable rather than zero for an absent full-suite comparator. Record input paths, selected inventory, fallback reason, command and commit.
- **T3: Match the assigned scope.** A small change uses its chosen check and a short report. An ordinary implementation uses its affected tests locally on its task branch. A batch verifies the affected merged candidate. If assigned full candidate validation, one owner coordinates the release's whole suite through `run_tests`, plus application/test types, build/language checks, browser engines where relevant, quality measurements and actual database checks; no test in that stage checks or waits for another live program's work. Run that full stage once for its candidate; after a fix rerun failed and affected checks unless evidence of wider impact justifies more. Do not repeat a full stage on every author or merely because a role name suggests it.
- **T4: Sample semantic mutation.** When mutation is assigned, select changed risky pure functions without database/network/process imports, prioritizing money, access and security. Use covering tests and incremental results where the tool supports them. Keep dry strings/configuration out; at most one mutant per line. Report killed, survived, uncovered, compile_error and timeout separately; errors/timeouts are not kills, and configuration failure or zero tests is not a pass. The project/task's risk policy determines what blocks; money/access/security survivors require explicit resolution. Do not invent a clean metric from unavailable tooling.
- **T5: Keep the time budget.** On a test machine a test that needs no browser takes under 1 s and its file under 30 s, and a whole run of the fast profile takes under 5 minutes of wall time; browser tests keep the budget their project sets. A file over budget is a defect like a failing test. Bringing it back under budget is in scope for whoever touches it or is assigned it: split it, remove real waiting, share expensive setup, test logic directly instead of through the whole application. Rewrites unrelated to the task or the budget stay out of scope. The budget is read from a run's timings, never checked inside a test.
- **T6: Name the harm.** Request extra tests for a concrete possible wrong result, not low coverage alone. A bug fix starts with a failing regression. For a permitted visual-only check, name exactly what visual behavior is proved.
- **T7: Measure useful timing.** Record file/package/part time, name each file and test over the T5 budget, and rank other slow cases against the package's measured distribution; promise no time you have not measured. Do not use a performance ability to launch unassigned background work.
- **T8: Validate model checks.** Arithmetic and code checks use executable tests with rejection cases. Model judgments use a versioned example set labelled independently, including a hidden subset when practical, and an owner-set threshold. Run it when the prompt, model, inputs or labels change; count false accepts and false rejects separately. An unvalidated model judgment does not replace a required human decision.
- **T9: Keep checks deterministic.** Control clocks, timezone, ordering, random seeds, IDs and ports. An unstable test may be weakened or deleted quickly, never skipped; do not retry or quarantine it until a label turns green. Checks of access, identity and secret redaction are never weakened: fix their cause. Use shuffled-order checking when the assigned verification calls for it.
- **T10: Read receipts.** Evidence is the actual run and its complete log for the reviewed commit. A change check an author or reviewer ran in their own workspace, recorded with its command, output and commit, is such a run. A parser treating every outcome as success is broken. Reuse a passed result only when its exact candidate/fingerprint and scope apply; do not rerun a proved check for appearances. Missing, refused, stale or collection-only evidence is never PASS.
- **T11: Read quality measures honestly.** When assigned, run crapper and dryer in your own workspace over the changed comparison, using coverage from a completed applicable run rather than starting another coverage run. Unsupported languages are NOT_RUN. A new or more complex function at CRAP 10 or above needs resolution; unchanged old complexity is recorded separately. A duplicate scoring 0.8 or more requires removal or an explicit accepted reason. Read actual numbers and scope instead of demanding final metrics from every author. Compiler errors and timeouts are not passing quality results.

Install dependencies from the lockfile in your workspace once, and again when it changes. After you check out another commit or make a worktree, prepare its dependencies and the builds of the repository's own packages again, as the repository says, before a check: a "cannot find" of the repository's own package is a stale preparation, not a failed check. Run builds, types, lint/format, coverage, quality and changed-code mutation locally. Named browser test files also run there when the browser is present; installing it is allowed into a folder of your workspace named by `PLAYWRIGHT_BROWSERS_PATH`. A node's shared browser folder already holds the browsers of the repository's Playwright version and may be read-only: never install into it, and where a repository's own script installs browsers before its tests, run its test runner directly. Stop only processes you started, by their process id. Never stop them by name or pattern, as `pkill` or `killall` do: on a shared machine that ends other employees' checks. Report a blocked route with its exact missing condition. Check results do not grant access, authorize publication or replace independent Security before a sensitive shared-branch integration.
