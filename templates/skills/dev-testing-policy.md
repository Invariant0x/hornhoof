You can plan and read proportionate verification for an assigned software candidate.

Read the task's acceptance, gates and employee assignment first. They identify the actual checker and scope; this ability does not assign a downstream tester, a shared turn review or a fixed role chain. Use the check assigned by the owner for small work. Where a simple visual change may use a visual/shared check without a separate test, honor that choice without waiving protected approvals. A full validation is a distinct assigned scope, not a consequence of selecting this ability.

- **T1: Test behavior.** Put logic in pure functions with direct fast tests. At boundaries use narrow integration checks for the named contract and failure; keep only a few end-to-end flows. Test races, locks, permissions and data migrations on the real database when that risk is part of the check. Do not write tests merely for coverage or that duplicate a constant's spelling.
- **T2: Select impact explicitly.** During code authoring or review run affected tests in your own workspace right away, naming each test file. Use the project's selector to collect that inventory; a directory, glob, loop, variable or selection that cannot name files uses run_tests as a whole suite, split into groups over free machines on the exact commit. Never assume run_tests selects by itself. A new test file always runs. For migrations, schema, configuration, environment, routes, fixtures, string tables, scripts, installation, updates, shared packages, API contracts and templates, use the project's declared out-of-graph policy; an unavailable adapter or an unbounded impact takes the complete affected package rather than an empty selection. Migrations need fresh and upgraded data and both up/down when supported; report unsupported down explicitly. Collection is not execution: keep NOT_RUN for an unavailable selector, completed exact-version receipts for executed tests, and unavailable rather than zero for an absent full-suite comparator. Record input paths, selected inventory, fallback reason, run, parts and commit.
- **T3: Match the assigned scope.** A small change uses its chosen check and a short report. An ordinary implementation uses its affected tests. A batch verifies the affected merged candidate. If assigned full candidate validation, one owner coordinates the required whole suite, application/test types, build/language checks, browser engines where relevant, quality measurements, actual database and live program checks. Run that full stage once for its candidate; after a fix rerun failed and affected checks unless evidence of wider impact justifies more. Do not repeat a full stage on every author or merely because a role name suggests it.
- **T4: Sample semantic mutation.** When mutation is assigned, select changed risky pure functions without database/network/process imports, prioritizing money, access and security. Use covering tests and incremental results where the tool supports them. Keep dry strings/configuration out; at most one mutant per line. Report killed, survived, uncovered, compile_error and timeout separately; errors/timeouts are not kills, and configuration failure or zero tests is not a pass. The project/task's risk policy determines what blocks; money/access/security survivors require explicit resolution. Do not invent a clean metric from unavailable tooling.
- **T5: Keep scope.** Do not mass-rewrite slow old tests. Change an old test when its behavior or the source it checks is part of this task.
- **T6: Name the harm.** Request extra tests for a concrete possible wrong result, not low coverage alone. A bug fix starts with a failing regression. For a permitted visual-only check, name exactly what visual behavior is proved.
- **T7: Measure useful timing.** Record file/package/part time and slow cases relative to the package's measured distribution, not arbitrary fixed-minute promises. Do not use a performance ability to launch unassigned background work.
- **T8: Validate model checks.** Arithmetic and code checks use executable tests with rejection cases. Model judgments use a versioned example set labelled independently, including a hidden subset when practical, and an owner-set threshold. Run it when the prompt, model, inputs or labels change; count false accepts and false rejects separately. An unvalidated model judgment does not replace a required human decision.
- **T9: Keep checks deterministic.** Control clocks, timezone, ordering, random seeds and IDs. Diagnose a flaky result; do not retry or quarantine it until a label turns green. Use shuffled-order checking when the assigned verification calls for it.
- **T10: Read receipts.** Evidence is the actual run and its complete log for the reviewed commit. A parser treating every outcome as success is broken. Reuse a passed result only when its exact candidate/fingerprint and scope apply; do not rerun a proved check for appearances. Missing, refused, stale or collection-only evidence is never PASS.
- **T11: Read quality measures honestly.** When assigned, run crapper and dryer in your own workspace over the changed comparison, using coverage from a completed applicable run rather than starting another coverage run. Unsupported languages are NOT_RUN. A new or more complex function at CRAP 10 or above needs resolution; unchanged old complexity is recorded separately. A duplicate scoring 0.8 or more requires removal or an explicit accepted reason. Read actual numbers and scope instead of demanding final metrics from every author. Compiler errors and timeouts are not passing quality results.

Install dependencies from the lockfile in your workspace once, and again when it changes. Run builds, types, lint/format, coverage, quality and changed-code mutation locally. Named browser test files also run there when the browser is present; installing it is allowed. Only a whole suite or declared profile uses run_tests, split into groups over free compatible machines. Report a blocked route with its exact missing condition. Check results do not grant access, authorize publication or replace independent Security before a sensitive shared-branch integration.
