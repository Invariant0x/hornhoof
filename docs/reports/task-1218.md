## Architecture plan

### Where the time goes (measured on b5b304a1)

The profiles below were taken with a temporary setup file, which is not committed. It records a V8 CPU profile of the
test worker, plus wall time and process CPU time for each test.

**apps/node/test/main.test.ts.** 81 tests, at a load of 21. The tests took 27.9 s of wall time and 17.1 s of process CPU.
- The CPU profile is 57 % idle and 12 % "program", with 4 % in eventually().
- Every socket drop in a test that runs on the real clock waits for the node's real pause before it connects again:
  DEFAULT_BACKOFF.firstMs is 1000 ms, up to 1250 ms with jitter. Meanwhile eventually() turns the event loop over and
  over on setImmediate, so the wait also costs CPU.

| Test | Wall | CPU | Cause |
| --- | --- | --- | --- |
| reports a real SIGKILL ... | 5.5 s | 3.5 s | two child processes, each started through tsx (transform of the node's sources) |
| numbered messages: talks to a server of the build before | 3.6 s | 3.2 s | a server restart and two drops, each a real backoff pause |
| numbered messages: sends numbered messages again ... | 2.2 s | 2.2 s | two drops, real pauses |
| being removed: 3 tests | 1.2 s each | 0.9-1.0 s | one drop each, real pause |
| a hello with many ends: stays within what an older server takes | 1.1 s | 1.1 s | one drop, real pause |
| does not send a job's end again ... | 1.1 s | 1.1 s | one drop, real pause |
| harness, description and slot tests | 0.5-0.9 s | 0.05-0.4 s | real git processes (git init, clone), under 1 s |

**apps/web/test/Subscriptions.test.tsx.** 92 tests, at a load of 20. Worker CPU was 53 s; the profile sampled 71 s.
- No test waits on real time: the tests that use timers already run on fake timers. Wall time is CPU time stretched by
  the load. That is why the file took 28 s at a load of 11-14 and 178 s at Tests.
- By package: jsdom 30 %, React 16 % (jsxDEV alone is 13 %: development React takes a stack trace for each element it
  creates), dom-selector 16 %, react-dom 11 %, css-tree 3 %, Testing Library and dom-accessibility-api 3 %.
- By call in the test file:
  - openCards / openAll (67 uses): 23 s, 32 % of all CPU. getAllByRole('button', { name }) runs over the whole document,
    working out the role, name and visibility of every element. Then each card opens in its own act(), so the whole screen
    renders again once per card.
  - rowOf: 2.7 s, a role and name query over the whole document.
  - findBy* and waitFor polling: about 10 s, because each DOM change runs the role query again.
- 42 tests take over 0.5 s of CPU and 9 take over 1 s. The heaviest is the first test, at 4.1 s: it also carries the
  file's warm-up, the first render and the JIT.

### What changes

Node main.test.ts:
1. Reconnect tests: numbered messages (4), being removed (3), a hello with many ends: stays within, and does not send a
   job's end again. Each puts the node's timeouts on the fake clock before runNode, with the file's own fakeClock(). After
   each drop or server stop, the test moves past the pause with the file's own dropped()/comeBack() helpers. Where the
   server is down for a while, it moves through each backoff step. The wait is virtual instead of 1-1.25 s of real time,
   and the scenarios and expectations stay as they are. Tests that log nothing collect the node's log lines, which
   dropped() needs.
2. The real SIGKILL test keeps its real child process and the real SIGKILL of the first node. The second start runs
   runNode in the test process on the same folder: the same function the child runs, with the same kind of adapter. The
   expectations on its hello and on no node.stopping stay. This saves one tsx start.
   If one child still takes over 1 s, I ask the head before going further. The option is to build fakes/run-lifecycle.mjs
   once, in beforeAll, with esbuild (the same compiler tsx uses), and start the child from the result.

Web Subscriptions.test.tsx:
3. openCards finds the same buttons, by the same role and accessible name, within the plan tables only. It opens them in
   one act(), so one render opens every card. The row toggle uses a functional setOpen, so no click is lost.
4. rowOf and the findBy* queries that wait for the table look within the plans' region instead of the whole document.
   Each looks for the same role and name, so it finds the same element.
5. After 3 and 4, a second profile and a fresh time table name each test that is still over budget, and what it spends
   on. Each further step keeps every assertion and scenario. No test is deleted or skipped. If two tests check the same
   thing, the head decides first.

### Limit of "regardless of load"

Virtual time removes every real wait. What remains is CPU work: jsdom and development React in the web file, child
processes and git in the node file. Its wall time grows with the share of CPU the machine gives the worker. So next to
the wall time and the load of each run, the table also records the CPU time of each test, which the load does not
change. My aim is CPU well under the budget, so that wall time fits it at the loads seen here (about 20).

### Checks

- A table of each test's wall time and CPU time, before and after, for both files, with the load (uptime) of each run.
- 10 consecutive runs of each file with no failure, recording the load before and after each run.
- tsc for web and node, both with their tests; eslint of the two changed files. No run_tests and no full run.
- For each node test moved to the fake clock: one temporary run with the behaviour broken, for example no resend after
  a drop. It must fail, which shows the test still catches the fault. The break is not committed.
- The diff removes no expect line, and no testTimeout or hookTimeout changes.
