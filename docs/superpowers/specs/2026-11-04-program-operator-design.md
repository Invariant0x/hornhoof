# Program operator and complete Operations

Task #243, independent Codex proposal for #234. Design only; no product implementation.
Source baseline: `6ae552b6` (Hornhoof 0.6.1). References below identify existing code at that commit. Proposed names and defaults are decisions in this note, not claims about existing APIs.

Implementation authority is the rewritten task #245 of 2026-11-04 17:46 UTC. Its overrides include `OPS-PROGRAM`, tool registration through `tools/watch.ts`, five invocation reasons, and guarded decisions on current permission questions. Part B owns staffing and `tools/mcp.ts`. This original proposal is retained for design context; the [implementation plan](../plans/2026-11-04-program-operator.md) records the selected contract.

## Decision

Keep program evidence on the node and recovery cases on the server. A case permits investigation; it never grants permission to interrupt a running program. Add two operator controls, `program_screen` and `program_keys`, with a second guard at the node. Hire `OPS-OPER` as a normal Operations employee. Reconcile the required Operations staff through application logic, not company-specific SQL migrations.

The head's clarification in #243 is binding: the first 60 seconds start when the node registers an assignment delivery attempt, including waiting for readiness. Never paste the assignment into an unknown screen. Expiry opens a recovery case rather than failing `ready()` and losing the program before the operator can inspect it. Existing automatic handling of known harmless setup remains.

The brief says eight company templates. This checkout has nine, including `project` (`packages/protocol/src/index.ts:194`, `apps/web/src/templates.ts:17`). Apply the requirement to all nine and to an empty company. Do not silently exclude the ninth template.

## Data model and ownership

Part A adds three company-scoped tables in `apps/server/src/db/schema.ts`, with a generated structural migration and its metadata. No fixed company, employee, subscription or person IDs; no access grants in migrations.

1. `program_deliveries`: `id`, `companyId`, `agentId`, nullable `jobId`, `programInstanceId`, `sessionId`, `ordinal`, `kind` (`assignment`/`live`), `attemptedAt`, `receiptAt`, `firstActivityAt`, `finishedAt`, `outcome` (`pending`/`taken`/`not_taken`/`cancelled`), and a digest identifying the intended words. The message body stays in the existing conversation records. A receipt can mean queued or taken; retain that distinction. A queued receipt ends cause 1 but is not a successful live uptake for cause 3. Record delivery identities before any input attempt. A normal user text record is also sufficient evidence for the initial assignment; a generic `task_started` is not.
2. `program_operator_cases`: `id`, company/agent/job/instance, primary `reason`, `evidenceKey`, `deliveryId`, `evidence` (bounded JSON list of qualifying reasons/keys), `openedAt`, `deadlineAt`, `status` (`open`/`resolved`/`escalated`), nullable `operatorAgentId`, `operatorJobId`, `escalatedAt`, and structured resolution. Unique `(companyId, agentId, programInstanceId, reason, evidenceKey)`, plus a partial unique index on company/agent/instance while status is open. One active investigation per program instance; further eligible reasons join its evidence, without a second wake. Check consumed supplementary keys as well as the primary key before reopening. Uniqueness plus a transaction protects reconnect and concurrent delivery.
3. `program_operator_actions`: caller-supplied `id`, case, operator agent/job, target agent/job/instance, snapshot token, enum key, reason, `requestedAt`, `completedAt`, and result (`requested`/`applied`/`refused`/`unknown`). Unique `(companyId, id)`. Write the intent and its agent-journal entry before sending a key. Final acknowledgement updates the action and appends the result. A persisted `requested` is not proof the key was applied.

The node owns a fresh `programInstanceId` for each actual launch and a monotonically increasing evidence generation. A resumed provider session is not the same process instance. A delivery ID survives network retransmission. The server reserves the delivery ID and per-agent ordinal before dispatch; `job.run` and `agent.say` gain optional additive `{operatorDelivery:{id,ordinal}}` metadata. Reserving an ID is not starting the 60-second clock: that begins at the authenticated node's registered attempt. A transport send that never reaches the program is cancelled, not a failed uptake. The live-failure streak is per agent across turns/process restarts and moves, not per instance; a taken live delivery resets it, and instance replacement alone does not. For an alarm, bind the case to the instance of the third finalized failure; a stale instance makes it read-only.

Pending node evidence and action IDs use a small durable local outbox/cache and are acknowledged by the server; no unbounded in-memory history. Snapshots expire after 30 seconds or any relevant generation change. IDs, time bounds, enum keys and maximum payloads are validated at both edges.

The server uses durable cases and deadlines, never a timer per terminal viewer. Persist each evidence fact as a structured `agentEvents` message with `operatorEvidenceId`; a partial unique index on company and that UUID prevents replay before the fact updates deliveries/cases in the same transaction. Node monotonic elapsed time produces threshold evidence; server timestamps are for display, deduplication and waiting deadlines. A disconnected node does not produce a new claim that the program lacks receipts. Reconnection first reconciles the instance, delivery state, receipts and terminal actions. Completed deliveries/actions remain available under the same existing conversation-retention policy; never prune an unresolved case or pending action.

## Exactly four invocation reasons

Use an independent delivery observer in new `apps/node/src/terminal/program-operator.ts`, fed from existing hook/log ingestion and process exit handling. It runs without a browser or a new log line. It may request help but cannot end a running program because of silence.

| Reason code | Start and qualifying evidence | End/reset and deduplication |
| --- | --- | --- |
| `assignment_unrecorded` | Register an assignment delivery attempt immediately when the node takes `job.run`, before readiness. At 60,000 ms no matching program receipt has appeared. Waiting at an unknown setup screen counts. | Matching program-log user words or an authenticated provider prompt/queue receipt disarms it. Key acknowledgement, empty input box, elapsed time, node heartbeat and generic turn-start do not. Key: delivery ID. |
| `recorded_no_activity` | After the matching assignment receipt, wait 300,000 ms for the first own reasoning, text or tool-call event from that program turn. Preserve any already-observed activity when channels arrive out of order. | The first such activity permanently disarms this reason for this delivery. Never reset it to run again after subsequent silence. Provider status lines, user messages, queue receipts and screen changes are not activity. Key: delivery ID. |
| `live_words_not_taken` | Three finalized live delivery attempts in sequence have no taken receipt. Preserve the existing turn-end plus `UNHEARD_MS` grace and disappearance handling for provisional queued/held words. Persist both successful and unsuccessful outcomes. Count actual attempts that put words into the program, not unsupported Antigravity steering or offline sends. | A taken receipt resets the streak. Fold outcomes in delivery ordinal order so late callbacks cannot change the sequence. Multiple Enter attempts for one delivery count once. Threshold is reached at three; fourth and fifth failures in the same streak do not re-wake. Key: ID of the third failed delivery in that streak. |
| `startup_exit` | The launched child/pane actually exits within 60 seconds of launch, before first own activity. Include a zero exit code, signal, and launch/exec failure. This 60-second definition of "immediately" is an architect default. | First activity or expiry of the startup window disarms this special reason; a later crash follows existing failure handling. Explicit cancellation, update drain, intentional restart and normal turn completion are excluded. Key: program instance ID. |

Implement case creation in new server `modules/program-operator/cases.ts`; invoke it from authenticated node evidence. Replace only the repeated-unheard alarm's operator eligibility, retaining requeue semantics in `conversation/unheard.ts`. Do not reuse its current one-hour counter or send two alerts through `notifyFailure` and the new dispatcher for the same evidence.

When cause 2 fires, the agent may still be computing. The case permits a read-only snapshot, not keys. The operator reports what can be established or escalates; it never sends Escape to test liveness. A program that already emitted one own event may work silently for hours without an operator call. Do not connect `checkSilentTurns` to this dispatcher or reinterpret `signAt` as a rolling operator timeout.

Case routing targets an active `OPS-OPER` in the company's Operations department with a runnable subscription, excluding the target itself. Use the usual conversation enqueue mechanism, no high-priority interruption of the operator's current work. The queued wake carries structured `{caseId, targetAgentId, targetJobId, programInstanceId, reasons, deadlineAt}` plus a short instruction to read the screen. A case is persisted and its wake inserted in the same transaction. A uniqueness marker on the queued wake handles server restart. There is no periodic scan-and-wake of healthy agents.

### Waiting, resumption and missing operators

The proposed recovery deadline is **10 minutes from case creation**, including time in the operator's queue. This is an architect default, not an agreed CEO promise. The server checks due cases at least once per minute, so escalation is due at 10 minutes and delivered within the next minute. If no operator can run, or the operator is the stuck agent, escalate immediately rather than making a recursive case. If the operator becomes unavailable after assignment, the original deadline still applies; no repeated hiring or duplicate wake.

For cause 1 before program work, retain the same pane and original assignment while readiness is being investigated. The old readiness timeout must not call `failedTurn` during this bounded recovery wait. Known auto-setup still runs first. Once an operator key produces a recognized ready input, node readiness probing continues and the original assignment goes in once; only an actual program receipt closes the delivery case. If the program accepts the words meanwhile, cancel the stale operator investigation and revoke its snapshot token. Do not clear the pending words just because `tookTurn()` ran.

After `needs_owner`, `failed`, unavailable operator or deadline expiry: persist the reason, revoke key permission, notify the orchestrator once with the snapshot, and preserve the original words for explicit continuation. For a pre-work turn, finish the old job once with `agent_failed`, non-retryable `unknown` failure and specific case diagnostic such as `operator_timeout`; this is a recovery-deadline decision, not completion inferred from program silence. An escalated case is a per-agent delivery hold. `afterFailure` recognizes that case and suppresses generic retry/duplicate Operations notification; `queue.heldBack` blocks automatic task continuations for that agent while the case awaits recovery. Do not classify a silent operator as provider `setup` failure: that would put every agent on the node into `needs_setup`. Existing provider auth/setup behavior (`apps/server/src/modules/tasks/failures.ts:23`) remains for real provider evidence only.

Leave the pre-work pane and its recovery observer alive after this failed job, with no executable operator capability. The owner's terminal can still inspect it. Once the owner passes the screen, the node sends durable `program.recovery_ready` for the old case/instance only when readiness is recognized and no prompt/turn has started. The server locks the agent and case, checks no matching words were taken and no newer turn exists, inserts exactly one continuation (`continueOf=oldJobId`), transfers pending-word ownership to its new delivery ID, resolves the case and pumps after commit. The old failed job never becomes running again. Duplicate readiness facts return the existing continuation. A late taken receipt for the old delivery wins and cancels unsent continuation words. If the owner already started a real typed turn, adopt that existing turn for recovery instead of injecting a second assignment. Reuse the same pane/session while its identity and instructions remain valid; on process loss use the normal saved-session resume path, with the same pending-word reconciliation. Ordinary queued words cannot bypass this hold or repeat already-taken input.

For causes 2 and 3 on a working program, escalation or case timeout never calls `job.cancel`, restarts, types, or ends the target turn. Work continues and its pending words retain normal queue semantics. Cause 4 reports the real exit; it never invents a still-running turn. Recovery from that exit uses the existing explicit restart/retry machinery, not an operator shell or a key into a dead pane. The investigation cannot create a new fifth operator reason.

## Operator tool contract

Server implementation: new `apps/server/src/modules/tools/program-operator.ts`, called by `mcp.ts`. Register the controls only for `job.roleKey === 'OPS-OPER'` in Operations, and repeat the check inside every handler against current employment/role/case ownership. Part A exports the role ID as `PROGRAM_OPERATOR_ROLE`; part B uses that exact ID in its template. No broad `message_employee` grant and no new removable all-company terminal privilege. Reject the login terminal, shell-only panes, removed agents, self-control, other companies, absent sessions, API-only targets and cases assigned to another operator.

### `program_screen`

Input: `{ employee: UUID, case: UUID }`, strict. A read-only snapshot may inspect an active program for an assigned case, including cause 2; viewing does not touch or interrupt the program. It must not launch a new agent session, change its size, set up a writable viewer or start a turn.

Example result metadata:

```json
{"case":"CASE_UUID","employee":"TARGET_UUID","job":"JOB_UUID","instance":"INSTANCE_UUID","snapshot":"OPAQUE_TOKEN","state":"pre_work","keysAllowed":true,"refusal":null,"cols":160,"rows":48,"capturedAt":"2026-11-04T15:00:00Z","image":"ATTACHMENT_UUID"}
```

MCP returns metadata/text plus a PNG image content block. Capture the actual existing tmux pane at its current dimensions, with zero scrollback and ANSI attributes, then redact at the node before transmission and again on the server before storage. Never send an unmasked screen merely to render it. A node response is at most 64 KiB of terminal cells, a rendered image at most 1 MiB; refuse oversize rather than return misleading clipped choices. For a dead program return its saved last pane, marked `gone` with `keysAllowed:false`.

Add a small server-side grid-to-PNG renderer in the new operator module, using `@resvg/resvg-js` and a bundled monospace font for Latin/Cyrillic. Escape every cell as text; strip non-display escape/control sequences, OSC links and clipboard operations. Render on the server so Mac nodes need no browser or new native package. This is a picture of the same pane/cells, not a second interactive process; font rasterization can differ from the browser terminal. Add the dependency/lockfile only in A. Store the PNG as a case-bound internal attachment and return its image ID for escalation; do not put bytes or base64 in journal messages. Reuse image validation/storage conventions at `apps/server/src/modules/tasks/attachments.ts:76`, extending authorization narrowly to the case and orchestrator. The target's ordinary department access does not give other employees access to the picture.

### `program_keys`

Input: `{ employee: UUID, case: UUID, snapshot: opaqueString, action: UUID, key: "Enter" | "Up" | "Down" | "Left" | "Right" | "Tab", reason: nonemptyString(max 500) }`, strict. One key per call, one fresh screen before the next call. No raw bytes, pasted text, commands, hotkeys, control characters, Escape, Ctrl-C or Ctrl-D, even in setup. This bounded v1 handles the requested harmless menus without becoming a shell.

Example result: `{"action":"ACTION_UUID","result":"applied","key":"Enter","journaled":true}`. `applied` means tmux accepted the key, not that recovery succeeded. Return stable errors `operator_forbidden`, `case_closed`, `program_busy`, `input_not_proven`, `snapshot_stale`, `node_unavailable`, `unsupported_node`, `no_program`, `protected_screen`, `action_unknown`. Invalid input is 400, invalid token 401, denied capability 403, missing/not-owned target 404, stale/busy state 409, missing node/capability 503. MCP marks these results `isError` and preserves the code/reason.

The node guard runs immediately before the actual key write, after draining current program evidence, under the same per-agent serialized lane as program start, initial/live input, browser input and cancellation. Re-check the case capability, instance, screen generation/hash and provider event generation after any awaited operation. The server's prior opinion is never sufficient. Reject a stale snapshot rather than queue its key for later. A browser key or new turn revokes the snapshot too. A test must introduce a real program-start event while the guard is waiting and prove no key reaches tmux.

Allowed key states:

| Node evidence | Keys |
| --- | --- |
| Newly launched agent program, no initial paste/accepted delivery/turn-start/own activity, pending setup case, matching fresh pane | Allowed for harmless setup only. This is `pre_work` even if the server job is running. |
| Program's own authenticated event says it is waiting for input and its blocking question is still current | Allowed only for a harmless informational prompt. This explicit current wait takes precedence over the historical fact that a turn started. Treat a permission, terms, identity or purchase request as protected. Cause 2 remains read-only; a late first own event resolves it rather than enabling keys. |
| No current proven harmless input-wait, and assignment was pasted/queued, program turn started, thinking/tool/retrying, or state cannot be proved | Refused. A timer does not turn any of these into pre-work. A pasted-but-unrecorded prompt requires escalation, never speculative Enter. |
| Gone, shell prompt, stale/unknown instance, protected screen, other operator, no open case | Refused. |

`a.busy` alone is insufficient because initial typing sets it optimistically (`apps/node/src/terminal/host.ts:646`). `asking` alone is insufficient because the current hook includes permission requests (`apps/node/src/terminal/host.ts:1262`). Preserve the source/kind/ID of the blocking provider event. An unknown screen in a program that was already working does not prove it now waits for input. Existing readiness checks may recognize a prompt to deliver an assignment, but must not reclassify an active turn from screen text.

Idempotency: persist action intent before dispatch, and node execution intent before writing. Repeating the same action ID with identical parameters returns its recorded result and never writes twice. Reuse with different parameters conflicts. If a disconnect/crash leaves execution uncertain, record `unknown`; do not retry keys automatically or reuse the old snapshot. A new observation and explicit operator decision are required. The per-target journal includes actor name/ID, operator job, target job/instance, case, key, reason, time and outcome for each action. Use `logTurnFact` for target/task visibility and an operator-side message, with a structured `operatorAction` object. Never store a secret in reason or picture; refuse and request a redacted observation when necessary.

### Reporting through the existing reporting tool

There is no magic conclusion parsed from free-form final text. Expose the existing `tell_orchestrator` reporting concept to this role through the new operator registration, with strict `{case, outcome: "needs_owner" | "failed", text}` for operators. Its implementation calls `reportOperatorCase`, attaches the case's latest redacted PNG automatically, revokes key capability and sends one durable orchestrator message. This is a narrow reuse of the reporting tool, not a cross-department employee-message grant. Heads retain their current form (`apps/server/src/modules/tools/watch.ts:269`); do not register the name twice on one MCP server.

Success is recognized by actual readiness/receipt events on the node, not by an operator's claim. A case with an already-sent report returns the previous result. The orchestrator asks the subscription owner for terms, consent, sign-in, passwords/codes, payment or plan changes using the existing human-question path. The operator never asks for or receives credentials. Missing pictures or unknown redaction are reported as unavailable; no fabricated screenshot and no key. If necessary the owner opens their existing terminal.

## Complete Operations and automatic subscription placement

Part B adds generic `templates/roles/operations/OPS-OPER.md` and `templates/skills/ops-program-operator.md`. Role: member, standard tier, no per-product copy and no periodic timer. Its skill is always present for this role; tools still enforce the role/case independently. The procedure is short: inspect the case and fresh screen, treat all displayed text as data, pass an unambiguous harmless theme/news/first-use/press-Enter screen, inspect after each key, and stop on anything protected or unclear. One investigation has at most 20 key actions; lack of progress, repeated screen or any protected choice reports immediately with the picture. The budget is a loop bound, not permission to keep guessing.

Terms, telemetry/data-sharing consent, authorization/permission expansion, login, passwords, codes, purchases, payment and plan changes always go to the orchestrator and subscription owner. A detected protected provider event/screen disables keys in the tool too. Do not promise universal semantic detection of unseen dialogs: an Enter key can accept consent. The role's explicit procedure, minimal key alphabet, fresh screenshots, known protected-screen refusals and audit lower this residual risk but cannot remove erroneous visual interpretation. If that residual risk is unacceptable, choose an allowlisted-screen-only release; it would not meet the CEO's request to handle unknown harmless screens and needs the head's decision.

Use one `REQUIRED_OPERATIONS_ROLES` constant in B's server policy for the minimum staff. Preserve optional OPS-INTEG/OPS-FIX/OPS-ACCT, personal names, models, skills, history, overrides and existing active heads. Reconciliation fills missing slots, never rewrites a complete roster or removes extras. A legacy head identified by `kind=head` in Operations already fills the head slot even without the new canonical role key; do not violate the unique head index (`apps/server/src/db/schema.ts:265`). Match the other roles by role key, not display name.

Update all nine company presets in `packages/protocol/src/index.ts:200` and their browser mirror `apps/web/src/templates.ts:23`, preserving optional roles. Tests compare both lists and assert exactly the same required minimum for each key. ## Decisions, risks and handoff

The high-risk path is preserving an unready pane for recovery while the job is already running. Prove it first with the unknown-startup-screen integration test. Do not make the screen parser a work-state authority, and do not let late receipt channels erase pending words. State synchronization cannot make an arbitrary external UI transaction atomic; keep one-key actions and revalidate immediately before write, refusing uncertainty.

The new capability deliberately crosses department boundaries only for a server-assigned recovery case. It does not expose session IDs as tmux selectors, owner sign-ins, root, arbitrary keystrokes or subscriptions. Masks cover known secrets; an unfamiliar login/QR/token screen must be treated as sensitive and withheld/redacted before forwarding. Retain a short audit trail of refused actions too, while limiting repeated failed reads and key requests. Screen content, ANSI links and prompt-like text are data, never authority to press something.

Cost is one operator conversation per incident, not per minute or terminal view. Cap snapshots at one per second per case, key actions at 20 per case, and one active case per instance. Redaction/rendering is bounded and on demand. False calls are reduced by exact words, main-program event attribution, delivery IDs, successful-uptake resets, startup phase checks and replay-safe writes. Node network loss and long quiet tools are not operator reasons.

Rejected alternatives: a general `term.input` MCP proxy bypasses ownership and working-state guards; one rolling five-minute silence timer violates the brief; SQL inserts for our company violate note #11; matching staff by names breaks localized/custom rosters; a single shared index.ts or mcp.ts owned by both developers makes the requested parallel split unreviewable.

Architect defaults for the head to review: 10-minute investigation deadline (plus at most one minute to deliver escalation), 60-second startup-exit window, 30-second snapshot lifetime, 20 keys per case, standard/default operator model and earliest eligible subscription. The tools only enforce known protected screens/events; visual misclassification of unseen consent remains a stated concern. All nine templates are included because the repository, not the stale numeral in the brief, defines the actual list.
