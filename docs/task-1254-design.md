# Contact values for outbound templates

Task 1254, known behavior, data risk. Base: 82d62a6bebb3ffde6c21ae89274d85ece89b5685 (released main, as directed by the head on November 17). Work stays on task-1254 for a separate 0.31.1 release. No old turn-31 history is integrated.

Contact values are encrypted JSON in a new outbound_contact_fields table, scoped by company, department and contact. Contacts and suppression remain company wide. Department scoping prevents another department from changing the values used in an approved message. The contact lock already used by consent and dispatch serializes updates. Missing records mean no optional fields, not a compatibility path.

Field names match [a-z][a-z0-9_]*, up to 80 characters; account_label and channel_name remain reserved sender fields. Up to 50 contact fields each contain one nonempty line of at most 200 characters. The existing approved variable catalog entry names that field, so outbound_submit keeps references only. Rendering combines department contact values with sender values and applies the existing clean check. Missing or invalid contact values produce explicit reason codes for that address; other submissions proceed independently. Dispatch re-renders, preserving existing byte-bound approvals and invalidation.

POST /api/outbound/contacts accepts optional fields. A new outbound_contact_add MCP tool calls this same route with the department head's existing person authority and returns ids only. Its privacy metadata hides private arguments from tool transcripts. No field values appear in setup logs, contact lists or agent replies. Re-adding an existing consenting address merges provided fields; suppression and revoked consent keep their current rules.

POST /api/outbound/contacts/import accepts channelId, filename, base64 data, source and evidence. A bounded CSV/XLSX reader processes address and consent columns; other valid identifier columns become fields. Consent must explicitly be true, yes or 1. Missing address, missing consent, invalid values, excess cells and suppression skip the row. Results contain only counts, row numbers and stable reason codes. Invalid or duplicate headers reject the file. Workbook formulas are never evaluated, file size/row/column and expanded ZIP limits bound resource use. First worksheet only, stated in the form. The same addContact and setup logging paths handle accepted rows.

The department screen adds repeatable field name/value controls and an import form using existing Field, form, button and spacing styles. English and Russian copy describe the CSV/XLSX contract. Validation puts focus on the first bad control. No sending is triggered by adding/importing contacts.

Checks: RED/GREEN named server tests for storage, MCP, render/admission/dispatch, isolation, consent, CSV/XLSX and privacy; migration fresh/upgrade/reapply and database grants; named web behavior tests; browser screenshots of add fields and focused error across three engines, supported themes, narrow/wide widths and shipped language extremes; builds, server/web/protocol types and changed-file lint. No full suite or run_tests. Migration uses the first free journal slot, currently 0137 (idx 136); the head renumbers at integration. Down migrations are not provided by this repository.

Threat boundaries: only existing department owners/head principals may add/import; private values remain encrypted and absent from reports/logs; strict field identifiers and bounded parsers reject malformed files; imported text is plain data and goes through clean at render; existing quotas, consent, stops, reviews and approvals remain unchanged.
