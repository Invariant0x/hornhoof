### Q6. SIGKILL обертки освобождает слот при живой detached-команде

Блокирующая, принята главой. Найдено после сведения b8: apps/node/src/check-command-runner.ts:75 (b8), held освобождал слот по close запроса, доверяя обертке очистку. При SIGKILL обертка этого сделать не может.

Происхождение: concern главы и собственная проба нашей цепочки. RED-коммит `978fabd35c4a81d6a6ca05035dd47fb3cbbfbafd`, тест `keeps no running group past the slot when its wrapper is killed`: в момент release команда жива, assertion ожидал false и получил true, exit 1. После пробы ее процесс убран тестом.

Исправлено `e92c3987fd530c6614603cb4acc16a7ce38a9ed0` в пределах узкой архитектуры главы. CLI сначала создает ожидающего лидера группы, передает pgid и /proc starttime. Настоящая команда получает разрешение только после slot. До этого разрыв IPC завершает лидера без payload. Узел проверяет связь лидера с аутентифицированным caller PID, uid, session, pgid и starttime. После close запроса или потери аренды очистка принадлежит узлу: TERM, KILL после 5 секунд, release только после отсутствия живых членов группы. Если остался только ожидающий лидер, он убирается сразу.

Сигнал отправляет отдельный короткий помощник под uid/gid группы, в том числе когда узел root. Непосредственно перед сигналом он повторно проверяет starttime и группу. Произвольная команда на узел не переносилась.

**Поправка Review (R1):** утверждение «лидер остается якорем до очистки» на e92…a2 не выполнялось в настоящем процессе. Тест check-command-child подменяет process в VM, а в настоящем процессе лидер выходил сразу после конца payload и отключения обертки: обработчики сигналов не держат цикл событий. Что payload оставил в группе, жило дальше без якоря. Узел такой группе не сигналит (Q7), держал слот и через 10 с закрывал машину для всех новых проверок, пока процессы не уйдут сами. Исправлено в `3cdc7ed41`: под слотом лидер живет и после payload, при очистке узел шлет сигнал группе. После завершения payload запускается таймер: если за следующие 60 секунд узел не убрал группу, лидер сам шлет ей SIGKILL. Это не срок от исчезновения узла.

На `49d006478171c8cac4cf5639b4f6cc4d45647870` исходная SIGKILL-проба проходит: в момент release команда мертва, 1 passed, exit 0, остальные 18 случаев файла не запускались этим вызовом. Позже независимый полный запуск этого файла дал 19 passed и exit 0; он указан в квитанциях ниже. На виртуальном времени проверены TERM/KILL, удержание слота до конца очистки и владение очисткой при конце аренды, токена и запроса.

### Q7. Потерянный исходный лидер нельзя заменить произвольным членом нового pgid

Находка собственного ремонта e92, блокирующая по безопасности. В apps/node/src/check-group.ts:63, :87 (e92) поздний выбор произвольного члена группы мог принять повторно использованный pgid, если исходного лидера уже нет. RED записанного случая: 1 failed, 12 passed; вместо отсутствия сигналов получены TERM и KILL.

Исправлено `1a4fc21bb8b677fd670e90991ffafbe1064c9b91`: для нового сигнала нужен именно исходный ожидающий лидер с тем же starttime. Если достоверная идентичность утрачена, узел не сигналит возможной чужой группе и не выдает освобождение слота за доказанное. Текущий check-group.test.ts: 13 passed, exit 0.

### Q8. Лидер группы мог сообщить 0 раньше получения CLI кадра stop

Находка своего ремонта 1a, блокирующая для честного статуса отмены. Место 1a: apps/node/src/check-command.ts:134, PARKED_CHECK. Лидер ловил TERM/INT/HUP, но после exit 0 payload пересылал именно 0. Если кадр stop еще не прочитан оберткой, отмена становилась успехом.

Без ОС и без реальных сроков получен RED: 3 failed / 3 passed, пересланы code 0 / signal null вместо пойманного сигнала. Исправлено `49d006478171c8cac4cf5639b4f6cc4d45647870`: лидер сохраняет имя пойманного сигнала и передает его с code null независимо от статуса payload. check-command-child.test.ts: 6 passed, exit 0. Остальные три случая подтверждают запрет запуска до допуска, ранний disconnect и сохранение лидера для узловой очистки.

## Отказ и восстановление машины

По дополнительному решению главы группа, не исчезнувшая после KILL, сохраняет слот. Через 10 секунд узел отказывает новым проверкам, отменяет еще не начатые ожидания и сообщает noRuns с причиной. Уже работающие чужие проверки этим не отменяются. Причина видна в Machines через checkError и записывается в журнал. Как только группа исчезла, отказ снимается автоматически и слот освобождается. При исчезновении самого узла действует прежний серверный срок аренды.

Это проверяется виртуальным check-group.test.ts и check-client.test.ts, а показ причины новым случаем Machines.test.tsx. Серверный путь передачи/очистки причины проверен независимым node-programs.test.ts: 2 passed, exit 0; полный вывод прочитан. Недостоверная таблица процессов или отсутствие исходного лидера не считаются доказательством очистки: машина сохраняет явный отказ до исчезновения группы.

## Согласованная граница платформ

По решению главы новая автоматическая PATH-обертка --wait устанавливается **только на Linux**. На Mac остается прежний прямой node-запуск turn-31. Очереди для tsc/vitest на Mac в этой задаче нет; точная идентичность процесса и своя платформенная проверка остаются предложением на turn-32.

Именованный check-command-platform.test.ts подменяет platform: на darwin node-обертка отсутствует и записанные tsc/vitest идут напрямую; на linux обертка есть и передает --wait. RED на прежнем установщике: darwin failed, linux passed. GREEN: 2 passed, exit 0. Запуск на реальном Mac не выполнялся.

Обычный hh-check сохранен. Без HH_BRIDGE --wait запускает локальную команду напрямую. При недоступном bridge, отсутствии хода или явно отключенной очереди сохранен незарезервированный запуск исходного дизайна. Отказ аутентификации, поврежденный поток до slot и явная ошибка узла не превращаются в такой fallback. Очередь поэтому не является жестким пределом параллелизма при недоступном координаторе.
