### Q2. Письмо обычного хода-носителя может не вернуться после его срыва

Восстановление после failed в afterJob ограничено job.inboxWake; у обычного носителя он false.

Две пробы с полной подготовкой компании упали по timeout до проверки результата. Минимальная `apps/server/test/inbox-carrier-recovery.test.ts` создает только нужные записи; локальные процессы оборвались 143 после RUN. Это не воспроизведение потери письма. Глава разрешил NOT_CHECKED при невозможности подтвердить; минимальная проба передана ревьюеру Claude. Ее результат еще ожидается.

### Q5. Отмена обертки могла стать 0 или оставить бесконечную команду

### Q6. SIGKILL обертки освобождает слот при живой detached-команде

Блокирующая, принята главой. Найдено после сведения b8: check-command-runner.ts, held освобождал слот по close запроса, доверяя обертке очистку. При SIGKILL обертка этого сделать не может.

Происхождение: concern главы и собственная проба нашей цепочки. RED-коммит `978fabd35c4a81d6a6ca05035dd47fb3cbbfbafd`, тест `keeps no running group past the slot when its wrapper is killed`: в момент release команда жива, assertion ожидал false и получил true, exit 1. После пробы ее процесс убран тестом.

Исправлено `e92c3987fd530c6614603cb4acc16a7ce38a9ed0` в пределах узкой архитектуры главы. CLI сначала создает ожидающего лидера группы, передает pgid и /proc starttime. Настоящая команда получает разрешение только после slot. До этого разрыв IPC завершает лидера без payload. Узел проверяет связь лидера с аутентифицированным caller PID, uid, session, pgid и starttime. После close запроса или потери аренды очистка принадлежит узлу: TERM, KILL после 5 секунд, release только после отсутствия живых членов группы. Если остался только ожидающий лидер, он убирается сразу.

Сигнал отправляет отдельный короткий помощник под uid/gid группы, в том числе когда узел root. Непосредственно перед сигналом он повторно проверяет starttime и группу. Произвольная команда на узел не переносилась.

На `49d006478171c8cac4cf5639b4f6cc4d45647870` исходная SIGKILL-проба проходит: в момент release команда мертва, 1 passed, exit 0, остальные 18 случаев файла не запускались этим вызовом. Полный файл ожидается отдельно. На виртуальном времени проверены TERM/KILL, удержание слота до конца очистки и владение очисткой при конце аренды, токена и запроса.

### Q7. Потерянный исходный лидер нельзя заменить произвольным членом нового pgid

Находка собственного ремонта e92, блокирующая по безопасности. В check-group.ts поздний выбор произвольного члена группы мог принять повторно использованный pgid, если исходного лидера уже нет. RED записанного случая: 1 failed, 12 passed; вместо отсутствия сигналов получены TERM и KILL.

Исправлено `1a4fc21bb8b677fd670e90991ffafbe1064c9b91`: для нового сигнала нужен именно исходный ожидающий лидер с тем же starttime. Если достоверная идентичность утрачена, узел не сигналит возможной чужой группе и не выдает освобождение слота за доказанное. Текущий check-group.test.ts: 13 passed, exit 0.

### Q8. Лидер группы мог сообщить 0 раньше получения CLI кадра stop

Находка своего ремонта 1a, блокирующая для честного статуса отмены. Место: check-command.ts, PARKED_CHECK. Лидер ловил TERM/INT/HUP, но после exit 0 payload пересылал именно 0. Если кадр stop еще не прочитан оберткой, отмена становилась успехом.

Источник: чтение IPC-пути и VM-проба самого нашего скрипта с записанными событиями. Без ОС и без реальных сроков получен RED: 3 failed / 3 passed, пересланы code 0 / signal null вместо пойманного сигнала. Исправлено `49d006478171c8cac4cf5639b4f6cc4d45647870`: лидер сохраняет имя пойманного сигнала и передает его с code null независимо от статуса payload. check-command-child.test.ts: 6 passed, exit 0. Остальные три случая подтверждают запрет запуска до допуска, ранний disconnect и сохранение лидера для узловой очистки.

По дополнительному решению главы группа, не исчезнувшая после KILL, сохраняет слот. Через 10 секунд узел отказывает новым проверкам, отменяет еще не начатые ожидания и сообщает noRuns с причиной. При исчезновении самого узла действует прежний серверный срок аренды.

Это проверяется виртуальным check-group.test.ts и check-client.test.ts, а показ причины новым случаем Machines.test.tsx. Серверный путь передачи/очистки причины добавлен в node-programs.test.ts; его выполнение ожидается на другой машине. Недостоверная таблица процессов или отсутствие исходного лидера не считаются доказательством очистки: машина сохраняет явный отказ до исчезновения группы.

## Согласованная граница платформ

По решению главы новая автоматическая PATH-обертка --wait устанавливается **только на Linux**. На Mac остается прежний прямой node-запуск turn-31. Очереди для tsc/vitest на Mac в этой задаче нет; точная идентичность процесса и своя платформенная проверка остаются предложением на turn-32.

Именованный check-command-platform.test.ts подменяет platform: на darwin node-обертка отсутствует и записанные tsc/vitest идут напрямую; на linux обертка есть и передает --wait. RED на прежнем установщике: darwin failed, linux passed. GREEN: 2 passed, exit 0. Запуск на реальном Mac не выполнялся.

Обычный hh-check сохранен. Без HH_BRIDGE --wait запускает локальную команду напрямую. При недоступном bridge, отсутствии хода или явно отключенной очереди сохранен незарезервированный запуск исходного дизайна. Отказ аутентификации, поврежденный поток до slot и явная ошибка узла не превращаются в такой fallback. Очередь поэтому не является жестким пределом параллелизма при недоступном координаторе.
