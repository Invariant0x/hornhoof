# Your task, from the build lead: a flaky test, a bug fixed at its cause

Your lane: `/home/altera/hornhoof-network/wt/bflakeweb`, Hornhoof repo, branch `task-bflakeweb`. Kind: bug. Read `systematic-debugging` first. Rule from the letter: "a flaky test is fixed at its cause, never retried".

**What happened.** `apps/web/test/AgentWindowCurrentTask.test.tsx` failed once in another task's author check on home-api, under coverage, on a loaded machine: `findByRole('button', { name: 'Task' })` at `:28` or `:63` did not find its button in time; the same code passed on the next run. Log of the red: `/home/altera/hornhoof-network/network-build/runs/remote-p1bt9-check-20261105-014415-1495413.log` (its tail cut the names; the writer who saw it named this test). Nothing that writer changed touches that test.

**What the lead sees, to be checked by you, not taken as the answer.** Testing Library's `findBy*` and `waitFor` give up after `asyncUtilTimeout`, 1000 ms by default, while `apps/web/vite`'s config sets `testTimeout: 20000`. `apps/web/test/setup.ts` does not set it. So every wait in the web suite rests on a one second clock, which a loaded machine can miss with no fault in the code. If that is the cause, the cure is one setting in `setup.ts`, well under `testTimeout`, because such a wait ends as soon as the element appears and a healthy test gets no slower.

**What is wanted.** Confirm the cause by evidence: reproduce it with a CPU hog of your own in your own run, or by showing the render takes over a second under load. First the failing test: a small direct test that an element which appears after a little over one second is still found. Then the setting. Then check the price: find tests that expect a wait to fail or an element to stay away, such as `.rejects` on `findBy` or `waitFor`, because they now wait longer; say how many there are and what the web suite's time was before and after. If some test would become slow, say which, and keep its old wait in that test with a word on why.

If it is not the cause, say so and find the real one. Look for the same one second clock in `apps/server` or `apps/node` tests only by reading, and name any in your reply. Your author check is the Hornhoof check of the hand-in steps. Change only what the cause needs. Keep the load moderate.
